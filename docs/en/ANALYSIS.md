# War of the Monsters (SCUS-97197): initial analysis

## Disc
- Volume `MONSTERS`, prepared by `INCOG INC` (Incognito Entertainment), published by SCEA.
- `SYSTEM.CNF`: `BOOT2 = cdrom0:\SCUS_971.97;1`, `VER = 1.00`, `VMODE = NTSC`.
- Main ELF: `SCUS_971.97` (7.4 MB), SHA1 `1ed7f8457436a9170d8f85386e267369c7fcdd4f`.
- "ROM" generated by splat (PT_LOAD as binary): SHA1 `250e3544aa99a04a2fd45974ff7ea38c31d0fc31`.
- IRX in `MOD/`: 989SND/989ERR (989 Studios sound driver), LIBSD, MCMAN, MCSERV, MTAPMAN, PADMAN, SIO2MAN and `IOPRP24.IMG`.
- Asset formats: `.NGP/.PTR/.RTX/.TEX` (level/monster models and textures), `.AIC/.AIP` (AI),
  `.CHR`, `.MRS`, `.BNK` (sound), `.VPK/.VAG` (ADPCM audio), `.PSS` (MPEG2 video).

## ELF
- **It is not stripped**: `.symtab` with 9,669 symbols, of which 5,381 are functions with a size (covering 98.8% of `.text`).
- C++ with **GCC 2.9x** mangling (`regen__6Pickup`, `__tf...`, `_vt$...`) and exceptions (`.gcc_except_table`).
- SCE toolchain: **ee-gcc 2.9x + newlib**. Sony libs version **2.4.0** (`PsIIlib* 2400`).
- The prologue saves registers with `sq`/`lq` (ee-gcc default).
- `.mdebug` (ECOFF + stabs) covers libgcc, newlib and the SCE libs, and **one game file, `hieri.cpp`, with complete types**
  (struct/class layouts, such as `HierLight`). Use `tools/mdebug_dump.py`.
- `.stab` contains only the lines of the VU microcode (`C:\CLEAN\MONSTERRT\COMMON\*.vsm/*.dsm`).
- `.vutext` (0x251020, 46 KB) and the `.DVP.overlay.*` sections hold the VU1/VU0 microcode.
- 294 named game classes (Monster, MonsterSound, Ai, Shell, Pickup, TheGame, ...).
- 45 TUs have static constructors (`_GLOBAL_$I$...`), which helps find the file boundaries.

## TU split
- gcc 2.x emits a local label `gcc2_compiled.` at the start of each TU's `.text`, followed by
  `__gnu_compiled_c` or `__gnu_compiled_cplusplus`, which gives exact boundaries and the language of each TU.
  The library TUs have their real name in `.mdebug`.
- `tools/find_tus.py` generates `config/tus.csv`, and `tools/apply_tus.py` rewrites the subsegments in the yaml.
- Distribution: `game/` 112, `common/` 71 (engine, `C:\CLEAN\MONSTERRT\COMMON`), `lib989snd/` 1,
  `gcc/` 21, `newlib/` 77, `sce/` 53 and `crt0`.
- The `game/` TUs are linked in **alphabetical order, case-insensitive** (makefile wildcard).
  The real names are unknown: the csv's `source` column says whether the name came from `mdebug`,
  from a `manual` choice (in `OVERRIDES`, guided by alphabetical order) or from a `guess` (dominant class or prefix).
- Adjustments needed for the match:
  - `subalign: 4`, because GAS aligns each object's `.text` to 16, but in the original the C TUs are at 8
    and newlib's `.S` files at 4.
  - `reloc_addrs.txt` (generated by `tools/gen_relocs.py`) forces raw immediates in 1,606 `%hi/%lo` pairs
    that spimdisasm resolved to the middle of `.text`. They are offsets into a large struct (`lui 0x12`), such as
    `0x120380`, not pointers.
- `tools/symdiff.py` lists the symbols that changed address in the generated ELF, useful when the checksum fails.

## Toolchain
- Reference test: `zipCrc32__FUlPCUcl` (`common/zip`) is zlib's `crc32` and matches exactly
  (source in `tools/cctest/crc32_variants/localptr2.cpp`; the original uses a local pointer `tab`
  declared after the `buf == 0` test).
- All Sony 2.95.x builds (273a/274/3-107/3-114/3-136) and SN v2.73a generate the **same** `.s` here.
  What decides it is the **assembler**: SN's `ps2eeas` expands `dli r,0xffffffff` as
  `addiu r,$0,-1; dsrl32 r,r,0`, and GNU as (old or modern) uses `lui 0xffff`. The symbols
  `sn_reg_frame`/`sn_dereg_frame` (libsn) confirm ProDG.
- `ps2eeas` does not understand splat's GNU syntax. That is why the build compiles with `-S`, rewrites the macros
  the SN way with `tools/snfix.py` and assembles with `mips-linux-gnu-as`. This allows `INCLUDE_ASM`.
  Macros without a known expansion make the build fail, instead of producing a silent mismatch.
- `tools/cc.sh` is the compilation pipeline, and `tools/setup_toolchain.sh` downloads the compiler into `tools/cc/`.
- `tools/ccmatch.py <src> "<flags>" [compiladores|project]` (`compiladores` = compilers) compiles and compares each function with the original.
  `tools/wsl/objdiff.sh <func> <obj>` shows the side-by-side diff.

## Data split
- `tools/find_data_tus.py` generates `config/data_tus.csv`, and `tools/apply_tus.py` writes the subsegments into the yaml.
- Evidence: (1) the local statics, grouped by object in `.symtab` (exact, and monotonic in all
  sections); (2) the `%hi`/`%lo`/`%gp_rel` references in each TU's code. A DP picks the monotonic
  assignment with the highest weight.
- The boundaries in stretches with no evidence (unreferenced data between two TUs) are arbitrary within the
  possible range. They do not affect the match, but may need adjustment when decompiling.
- TUs in `config/decomp_tus.txt` use `.rodata` (with a dot): rodata used by a single function migrates
  into the function's `.s` (INCLUDE_ASM), and shared rodata needs to be defined in the C/C++.

### Codegen rules learned
- `ps2eeas` decides `$gp` vs `lui` in a single pass (see Toolchain); that is why the **definition order of globals** matters.
- g++ 2.95: globals with an initializer (including dynamic ones) are emitted at the definition; those without an initializer go
  to the end of the file, in order of first declaration. A header `static const` is only emitted if used, at the end.
- String literals of up to 8 bytes go into `.sdata` (`-G8`).
- R5900 short loop: loops with fewer than 6 instructions get `nop`s (`snfix` does this; delay slots in `reorder` count).
- The scheduler tends to emit independent instructions in the **reverse order** of the source (e.g. consecutive stores).
- A store to a `char` field forces reloading globals (aliases with everything); `int` fields do not.
- `zipCheckHeader` and `zipGetChar` stayed `NON_MATCHING` (registers).
- A body that ends in inline `asm`: gcc leaves the delay slot to the assembler. `ps2eeas` puts a `nop` there; GNU as pulls
  the last instruction of the `asm` into the slot. `snfix` reproduces the `nop` (`.set noreorder` around the `j`).
- Matrices: `A3_A3_f` in the mangled name is `float[4][4]` (gcc 2.x records size-1). 64 B copies with `lq/sq t0..t3` are inline `asm`.
- `ptr = (char *)(idx * 64) + (unsigned)base` produces `addu a1,a1,v0` (result in `idx`'s register); `&base[idx]` does not.
- splat's per-function `.s` files diverge from the monolithic ones (`ACC` without `$`, `%lo(sym + (0x44000 & 0xFFFF))` without the `%hi` carry);
  `configure.py` fixes both after the split.

## Hardware boundary (first pass)
Dynamic view (what runs per frame in the port and the order for removing the emulator code): [steps/BOUNDARY.md](steps/BOUNDARY.md) (`docs/passos/FRONTEIRA.md`).
`tools/hw_boundary.py` generates `config/hw_boundary.csv` with, per TU, SDK calls, register accesses
(0x1000xxxx/0x1200xxxx), VU0 (COP2) instructions, scratchpad and calls to 989snd.
- **VU0 macro mode is in almost all game code** (2,681 `lqc2`, 1,426 `sqc2`, `vmulax/vmadday/vmaddz`...):
  they are inline vector math functions (matrix×vector, sum) with inline assembly. For the port, they should come
  from a math header, so replacing them with C++/SSE solves the problem in a single place. For the match, that header
  needs to reproduce the original inline asm.
- Direct register and DMA access is concentrated in the engine (`common/hier`, `texm`, `vi`, `ps`, `pkt`, `disp`,
  `blit`, `particle`...) and in `game/ui`. That is the render layer the port will rewrite.
- Sound: `game/Sound`, `game/StreamingSoundManager` and `game/ShellFinished` call 989snd (`snd_*`). Memory card: `game/McFile`.

## hieri types
`python tools/stabs2h.py disc/SCUS_971.97 include` converts the stabs of `hieri.cpp` (.mdebug) into C++ headers:
81 SDK types (GIF/VIF/DMA/GS registers as bitfields, `ThreadParam`, `sceDmaTag`...) and 89 engine types
(`_hierobject`, `_hiergroup`, `_animCharInstance`, `ParticleType`, FX enums...).
- Each struct has a `typedef char _size_X[sizeof(X) == N ? 1 : -1]`; the header compiles cleanly with ee-gcc 2.95
  (`tools/cc.sh`), so all the sizes match.
- Stabs do not keep `__attribute__((aligned))`; `infer_alignment` recovers the alignment (16) from the offsets.
- Methods (constructors, `operator=`) are dropped; only data, enums and typedefs remain. Opaque types (`ActHead`) only get a forward declaration.
- `long long` and `long128` are 128 bits in ee-gcc (`long` is 64).
- They only cover the engine in `common/hier*`; the rest of the game (`game/`) still has no types.

## Static recompilation (experiment from 2026-10-09)
Done with [PS2Recomp](https://github.com/ran-j/PS2Recomp) (commit 2c5fbb9), **outside the repo** (the generated C++ is game code: ~90 MB, 5,385 files).
- The ELF has symbols, so the analyzer finds 5,382 functions with name and size. It recompiles in ~1.4 s: 5,042 recompiled, 340 replaced by runtime handlers
  (SDK/libc/libm), **0 decoding failures, 0 unhandled instructions** (COP2/VU0 macro mode included). 432 functions have an indirect `jr`/`jalr` (`switch`) that the analyzer does not resolve
  (0 jump tables detected); the recompiler covers them with "fallback entries" (60,604).
- All the C++ compiles and links with the runtime. In the test runtime the game initializes: it loads the 7 IRX into the emulated IOP (989snd included), gets past the sound init and enters the
  menu loop (`userintMain`). The movies get stuck because the game's decoder (`decBs0`/`videoDec*`) waits for the IPU, which the runtime does not emulate; in the tests they were skipped by a hook
  (`playMpegMovie*` and the `updateMpegMovieDecoding` thread). Since 2026-10-10 the game runs on Windows (MSVC) with native drawing, sound, movies and keyboard (`native/`; status in [steps/NATIVE.md](steps/NATIVE.md), what is missing in [TODO.md](TODO.md)).
- The runtime already brings a CPU GS, VU and VIF1 interpreters and an emulated IOP; it is the bridge, not the destination (the destination is native rendering at the engine boundary). The emulated VU1 serves as the reference for the VU1 vs native check ([steps/VU1CHECK.md](steps/VU1CHECK.md)).
- **PS2Recomp bug found**: `SQRT.S fd, ft` reads the source from `ft` (uses |ft|) and `RSQRT.S fd, fs, ft` is `fs / sqrt(|ft|)`; upstream used `fs`. Affects 108 functions (`sqrt.s`) and 76 (`rsqrt.s`).
  **`div.s` and `rsqrt.s` by zero** (confirmed on 2026-10-18 by the METRO pedestrians; analysis in commit 7c1c24e): the generator emitted ±Inf
  (the EE saturates to ±FLT_MAX) and VU0 turned it into NaN (0 × Inf). Fixed in the WSL generator (`~/wotm-recomp`, `fpu_translator.cpp`: `FPU_DIV_S`/`FPU_RSQRT_S`) and in the
  runtime (`ps2_fpu_rsqrt` in the patch); 746 `div.s` and 134 `rsqrt.s` regenerated in `runner/`. Upstream fixed the same thing in PR #272. **Not yet verified**: `min/max` with NaN.
- **Bug in PS2Recomp's `rand` stub** (2026-10-18; upstream has it too): `std::rand() & 0x7FFF` instead of newlib's LCG (31 bits). `mathfRandf` uses the low 23 bits of `rand()` as the mantissa and came out in [lo, lo + 0.004·(hi - lo)). Fixed in the patch's `LibC.cpp`.
- **Our own bug found by the oracle**: gas encodes `sqrt.s` in the MIPS32 form (source in `fs`); on the EE that reads `$f0`. Fixed with `eeSqrtf` (`include/vecmath.h`).
- Coverage from boot to the menus (3 min, movies skipped): 786 distinct functions (97 matched, 31 equivalent, 601 asm, 57 hw). List of the 601 in `config/boot_coverage_asm.csv`.

## Function status conventions
Each function in the binary is in one of these states (`python3 tools/progress.py`, full table in `config/status.csv`):

| State | Meaning | How it appears in the code |
|---|---|---|
| `matched` | C/C++ that generates exactly the same bytes | function written in `src/`, without `INCLUDE_ASM` |
| `equivalent` | rewrite believed to be equivalent, but it does not match byte for byte | inside `#ifdef NON_MATCHING`, with `INCLUDE_ASM` in the `#else`; the comment states the score and the cause |
| `hw` | talks directly to the PS2 hardware or to SDK services; will be rewritten in the port's platform layer | listed in `config/hw_funcs.txt` (by TU or by symbol) |
| `asm` | still only in assembly | plain `INCLUDE_ASM` |

- The default build (`ninja`, `tools/wsl/check.sh`) uses the original assembly of the `equivalent` functions, so the ROM always checks out against retail. A build with `-DNON_MATCHING` would compile all the C++ rewrites (the base of the port).
- The `equivalent` functions are verified without unit tests (project decision): `tools/difftest.py` (retail vs ours in a MIPS emulator, same random state), `tools/recomp_oracle` (those with VU0 or `min/max/madd`), the halfcpp ELF in PCSX2 ([steps/PCSX2_TESTING.md](steps/PCSX2_TESTING.md)) and, incomplete, the guinea-pig runtime ([steps/NATIVE.md](steps/NATIVE.md)). `tools/verify_tu.py` runs all of that per TU. Real bugs already found by each of them are in [steps/PITFALLS.md](steps/PITFALLS.md) and [PCSX2_TESTING.md](steps/PCSX2_TESTING.md).
- Whoever wants to continue the byte-for-byte work: `grep -rn NON_MATCHING src/`; the comment next to each function says where it stopped. `tools/wsl/variants.py` and `tools/wsl/permute.py` try many source variations in parallel.
- `hw` code and library functions (`libs`) do not need to match: do not spend effort on them.
