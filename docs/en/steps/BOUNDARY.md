# Hardware boundary: what of the PS2 the port still uses and the order to remove it

(Docs index in [CLAUDE.md](../CLAUDE.md).) The goal of the port is an executable without emulator code: no VU1, VIF1 or GS on the CPU, no IOP interpreter, no emulated DMA, interrupts and timers. The recompiled game remains the base; whatever talks to the hardware gets replaced at the engine boundary (the game's call, not the register). The emulated parts remain useful as the **reference** for the VU1 x native check ([`VU1CHECK.md`](VU1CHECK.md)): since 2026-10-19 they have left the game executable (`wotm.exe`) and stay only in the test one (`ps2EntryRunner.exe`; step 5), and the IOP interpreter too (step 6), then the IOP RAM (step 9).

The static list (per TU: SDK calls, registers, COP2, scratchpad, 989snd) is `config/hw_boundary.csv` (`tools/hw_boundary.py`); the hardware functions are in `config/hw_funcs.txt`. This file is the **dynamic** view: what runs per frame in the live game and how each part is served today.

## How to measure (redo after each step)
- Run a fight with `PS2X_COVERAGE=<pasta>\cov` (the runtime writes `cov.<quadro>` every 300 screen frames, accumulated count per address) and, for a match without the menu, `WOTM_MATCH=3,1,1 WOTM_AIVSAI=1`.
- `python tools/hw_frame.py <pasta>\cov.1800 <pasta>\cov.4800` gives the calls per frame of the hardware functions, per TU; `--modo sce` shows the SDK, libm and libgcc; `--modo tudo` shows everything.
- EE CPU cost: `WOTM_FIELDLOG=1` (`[field]` lines, `host - ocioso` (host minus idle) per frame).

## State per subsystem (measured on 2026-10-18, AI x AI fight on stage 1, 3000 frames)

## Proposed order
1. **IRX out of the IOP** (done on 2026-10-18).
2. **IOP idle** (done on 2026-10-18, in the runtime patch: `iop_emulator.cpp` and the `[iop]` counters in `ps2_runtime.cpp`). With `WOTM_IRX=1` the modules load and the IOP runs again. Corpus with no regression (41 frames).
3. **Drawing packets out** (done on 2026-10-18, in the form below). The frame packet reads the native side did became hooks on the call that builds them: text, the `ScreenPolys` HUD, lens flare and, last, the fades and the menu bars (through the arguments of `rtFadeScreen`, `uiFadeScreen`, `letterboxDmaData` and `Shell::FadeScreen`, and through the level of `TheGame` on return from `updateFadeOut`/`updateFadeOutAndIn`; checked against the packet: 4,866 rectangles and 120 reads of `Shell::FadeScreen` in the menu, 587 rectangles in a fight with an end of round, no difference). No live reader reads a frame packet anymore; only the replay (`--vu1cmp`) reads the ones in the snapshot. **Cutting the builders (returning early outside the check frame) was not done, on purpose:** measured on 2026-10-18 (AI x AI fight, host time per frame), building costs about 0.2 ms of the ~6 ms of the EE (`pktAddVu1ObjAsm` 130 to 165 µs in ~200 calls, `pktLinkAlphaObjAsm` 6 µs, `spritePacketBuild`/`texSpritePacketBuild` ~5 µs, `psBldBlockerPkt`/`psEndBlkObjs`/`psFindActiveBlockers` ~10 µs, `fontSpritePrint` 8 µs; for comparison, `hier` ~1 ms and `TheGame::Update` ~0.7 ms). The packets stay in RAM as game data and their DMA is already discarded (`PS2X_NO_VIF1`), so they do not tie the executable to the emulators (step 5). And `pktAddVu1ObjAsm` is hand-written assembly, with its own convention (it reads `$s0`/`$s5`/`$s3` and `vf*` from `hierTraverseAsm` and returns state in the context in `$s0`): returning early requires redoing what it leaves in the context, a big risk for 3% of the frame. **`hierTraverseAsm` cannot be removed entirely**: it also animates, runs the control nodes, camera, light, particles, bones (the palette the native side reads), locators and LOD.
4. **Native clock and vsync.** Half done on 2026-10-18: the game timer reads the host clock (`timerGetCurTics` replaced entirely; `timer1Handler` adds the fields from the host time, counted on entry because resuming after `sceGsSyncV` does not go through the wrapper). `timerGetFieldCount`/`timerGetUpdateRate`/`timerGetFieldsLastFrame` only read what `timer1Handler` and `timerWaitForMinUpdateRate` write, so they already follow the host. Measured: 100% of real time with and without 2-field frames, same as the emulated timer ([`NATIVE.md`](NATIVE.md), "Timer pelo relógio do host" (timer from the host clock)). **Vsync done on 2026-10-19** (scheduler seam, `EeScheduler.cpp`, in the patch): `sceGsSyncV` waits for the `EeScheduler`'s VBlankStart, whose deadline required the wall clock *and* the virtual cycles. Now the deadline expires only by the host: `processDueDeadlines` removes the events whose `hostDeadline` has passed, without the pacing wait; the checkpoint of the generated code checks the nearest host deadline every 16 calls; idling (`waitForEvent`) waits for the deadline on the host and adds to the cycles the time it actually stood still. After a stall of more than 4 vblanks the grid restarts from now instead of firing the late ones all at once. The two patches were removed (virtual clock following the wall clock in `checkpointDue`, delay added in `waitForEvent`). Measured with `WOTM_FIELDLOG`, before and after: 1 vs 1 fight at 59.9 f/s and 100.1% of real time in both; with `WOTM_LOGICDELAY=25` (1- and 2-field frames), 100.1% and frames on the grid (16.7 and 33.3 ms; without the patches and with the vblank still by cycles it had given 19 to 31 ms and 138%); menu through the pad script up to the fight same as the old one (loads included); 4 monsters, 59.4 to 59.7 f/s; corpus with no regression. The emulated timer 1 (`WOTM_TIMER_EMU=1`) runs at ~1/3 of real time, because the cycles no longer follow the clock. **Open:** in the first runs with 4 monsters (`WOTM_MATCH=3,1,2,5,1`, 70 s) the new one had stalls of 0.2 to 1.2 s in 5 of 10 fights (the EE thread blocked outside the scheduler: little CPU, little idling), and the old one none in 3. In the next 10 fights of the new one without the sampler, none, and none in 9 more of the old one (5 of them alternated with the new one). With `PS2X_HOSTPROF` on (any mode, 15 fights) none showed up. On 2026-10-19, in `wotm.exe` after step 6: a batch of 10 fights without the sampler had two (319 ms in fight 8, a burst in fight 10); the next batch, with `PS2X_HOSTPROF=3` (stack of each frame above 100 ms), none in 10 fights. The 5 `[stall]` of that batch (78 to 149 ms) all fell in the stage load, before the fight (`Shell::LoadMonstersDB`, `fileReads`, progress bar). The sampler still seems to hide the stall. If it comes back: `WOTM_FIELDLOG` shows `cpu=` and `[stall]` with the game's pc, without an extra thread. Related to physics with `dt` and to `WOTM_RATEMIN`.
5. **VU1, VIF1 and GS out of the game executable** (done on 2026-10-19, CMake seam in the patch). The same build (`build_dev`) generates two executables from the same objects of the translated game (object library `ps2_game_code`, compiled once):
   - **`wotm.exe`, the game:** links with `ps2_runtime_game`, the `ps2_runtime` without the GS sources (`gs_frontend`, `gs_cpu_backend`, `ps2_gs_memory`) and the VU1/VU0 interpreter sources (`ps2_vu1_core/upper/lower`), compiled with `PS2X_HW_EMU=0`. In this mode `PS2Runtime` has no `m_gs`, `m_vu0` or `m_vu1` (the VU0 state of the translated microprograms lives in a `VU1State`); the VIF1 does not exist (the channel 1 DMA completes without processing; the VIF0 stayed until step 7); the GIF arbiter has no packet function (the GIF channel completes and the packet is discarded; the shortcuts that sent GIF channel chains straight to VRAM are gone); `sceGsExecStoreImage` returns black (one call at boot, 4x4 Z32, as it already came out with `PS2X_NO_GS`); the presentation has no GS frame (black background, with the native scene and the movies on top); `PS2X_NO_VU1/VIF1/GS` are always on through `main.cpp`; the check, the photos and `--vu1cmp` are left out (`wotm_vu1check.inc` only warns). A VU0 microprogram without a translation does not run (warning `[vu0] microprograma sem traducao` (microprogram without translation)); in `ps2EntryRunner` the same case falls into the interpreter with the warning `... no interpretador` (in the interpreter). Neither one showed up (menu, fights with 2 and 4 monsters, batch of 6 fights). In `wotm.map` no symbol of `VU1Interpreter`, `GS`, the rasterizer or the check remains.
   - **`ps2EntryRunner.exe`, the test one:** same as before (emulated parts, `WOTM_VU1CHECK`, `WOTM_FOTOS`, `--vu1cmp`, corpus).
   - **Who runs which:** `run_live.ps1` uses `wotm.exe`, except with `WOTM_VU1CHECK` or `WOTM_FOTOS` on, with `-Exe test`, or when `wotm.exe` is missing or out of date (guinea pig); `run_live.bat` turns photos on by default, so it stays on the test one, and the launcher (photos off by default) goes to `wotm.exe`. `corpus.ps1`, `vu1cmp.ps1` and `live_attack.ps1` call `ps2EntryRunner.exe` directly; `lote.ps1` watches both (with `-Check 0` it runs the game one).
   - **Measured:** menu through the pad script up to the fight and AI x AI fight with 4 monsters (`WOTM_MATCH=3,1,2,5,1`, 70 s) in both executables: 60 f/s, the same EE thread cost (`WOTM_FIELDLOG`), no drop; batch of 6 fights (`-Check 0`) with no drop or slowness; corpus in the test one with no regression. `wotm.exe` is only ~0.5 MB smaller (the emulated parts are small next to the translated game); the gain is not depending on them.
6. **IOP out of the game executable** (done on 2026-10-19, CMake seam in the patch). `wotm.exe` links with `ps2_iop_game` instead of `ps2_iop`: only the PS2 paths (`ps2_path.cpp`, which the VFS uses) and another implementation of `IopSubsystem` (`ps2xIOP/src/iop_subsystem_host.cpp`) with the IOP RAM on the host (2 MB, the same address and heap rules as `IopMemory`, so that `SIF.cpp` can allocate, read and write), RPC without a server and module loading that fails. This is what already happened with the IOP idle: without IRX, no RPC had a route. `ps2_runtime.h` does not change (the game code is compiled once for both executables), and `ps2EntryRunner.exe` keeps the emulated IOP. In `wotm.exe` `WOTM_IRX=1` is ignored with a warning.
   - **Measured:** in `wotm.map` no symbol remains of the IOP interpreter, kernel, imports or HLE modules (`mcserv`, `dbcman`, `libsd`); the executable is ~140 KB smaller. Menu through the pad script up to the fight, without any RPC or SIF. Memory card through the menu: "load game" reads the save and opens the match; "load settings" reads slot 1; "accept and save settings" (with audio in mono) asks for the slot and the confirmation and writes to `mc0/`; on the next boot the options come back in mono (`docs/screenshots/2026-10-19/2026-10-19_memory_card_sem_iop_gravar.png` and `..._ler.png`). AI x AI fight with 4 monsters (`WOTM_MATCH=3,1,2,5,1`, 70 s, `WOTM_FIELDLOG`), twice: 99.5% and 99.6% of frames in 1 field, 8.5 and 8.3 ms of host work per frame; in `ps2EntryRunner.exe`, 99.9% and 8.2 ms. The few ~50 ms frames (40 ms idle) appear in both executables. Corpus in the test one with no regression.
   - Without "load settings" or "load game" in the session, "accept and save settings" only applies the options and returns to the menu, without writing. It is the same in the test executable, so it comes from the game, not from step 6.
7. **VIF0 out of the game executable** (done on 2026-10-19). Measured before (counters on the channel 0 DMA, menu and fight): the VIF0 only receives MPG, always the same fixed chain from the ELF (two MPGs of ~1.5 KB, the whole VU0 code memory), sent by `hierInit` at boot and by `hierLoadVu0Ucode` every frame. No UNPACK: shadows and particles do not use the VIF0. `tools/vu0native.py` now writes into the `.gen.inc` the 4096-byte image that this chain leaves (`wotmVu0CodeImage()`), and in `wotm.exe` two hooks (`wotm_live.inc`, `wotmVu0UcodeInstall`) copy it straight into the code memory: `hierLoadVu0Ucode` becomes just the copy (which does nothing if the memory is already identical), and `hierInit` runs the original and copies right after, because the microprograms run before the first `hierLoadVu0Ucode`. Without that second hook, the program at 0x430 ran 4 times without code. The `processVIF0Data` of `wotm.exe` becomes a no-op (runtime seam, `ps2_vif1_interpreter.cpp`, in the patch) and warns once if anything arrives; what arrives is a 48 B packet at boot that only sets STMASK and STCOL (they only matter for UNPACK). In `ps2EntryRunner.exe` the VIF0 remains, and the hook only checks: on the second call of `hierLoadVu0Ucode` it logs `[vu0] microcodigo do VIF0 igual a a imagem gerada` (VIF0 microcode equal to the generated image).
   - **Measured:** in the test one, the code memory equal to the image. In `wotm.exe`, the image is copied only once at boot (afterwards the memory does not change anymore), and no `microprograma sem traducao` appears in the menu (pad script up to the fight) nor in the 4-monster fight (`WOTM_MATCH=3,1,2,5,1`, 70 s): 99.7% of frames in 1 field, 8.4 ms of host per frame, no stall. The fight looks normal on screen (`docs/screenshots/2026-10-19/2026-10-19_luta_4_monstros_sem_vif0.png`). Corpus in the test one with no regression.
8. **Scheduler: what the game uses, and the EE timers out of the game executable** (2026-10-19). Counted in the `EeScheduler` of `wotm.exe` (temporary counters, already removed), in the menu through the pad script up to the fight and in a 4-monster fight, over 600 vblanks:
   - **A single thread:** the main one (entry 0x100008), from boot to the fight, no other exists (the movies, which would create threads, are native). No `WaitSema`/`SignalSema` (there are 2 semaphores created and never used), `SleepThread`/`WakeupThread`, event flag or alarm.
   - **No INTC handler registered:** the vblank (causes 2 and 3, 600 of each) only writes the tick, the CSR field bit and the vsync flag, and wakes `sceGsSyncV`. **One DMAC handler**, the one from `hierSetDmaIntHandler`, called ~1 time per frame (end of the channel 1 DMA). Channel 2 (GIF) finishes ~5 times per frame without a handler.
   - **Timers:** only T1, ~2 reads and 3 writes of the count per frame (`timer1Handler`, `timerWaitForMinUpdateRate`) and the mode in `timerInit`; no timer interrupt. `timerGetCurTics` and the fields of `timer1Handler` already come from the host since step 4. T1 only feeds the base of the original `timerGetCurTics` (`D_006F8DC4`), which the replaced one does not read.
   - **Per frame:** one thread switch (the main one leaving idle after the vblank) and 27 to 47 thousand checkpoints of the generated code. According to the host sampler, `checkpointDue`, the clock it checks every 16 checkpoints and the scheduler loop add up to ~3.5% of the fight's wall time, ~0.5 ms per frame. That is the ceiling of the gain from replacing the scheduler.

   **Done:** in `wotm.exe` `accountCycles` no longer advances the EE timers or the IOP (runtime seam, `EeScheduler.cpp`, in the patch), and the GIF FQC does not go up (`ps2_memory.cpp`: the packet is discarded immediately, and the FIFO only drained through the timers advancing). `WOTM_TIMER_EMU=1` is ignored in `wotm.exe` with a warning. Measured (4-monster fight, 70 s, twice): 99.8% of frames in 1 field and 7.6 ms of host per frame (before, 7.9 and 8.4 ms). Menu through the pad script up to the fight the same. `ps2EntryRunner.exe` does not change.

   **What remains** (done in step 10, with the whole replacement): with one thread and no INTC, a native loop in `wotm.exe` would be: the main thread runs directly; `sceGsSyncV` waits for the host vblank and applies the tick, the CSR and the flag; the DMAC handler is called when channel 1 finishes; the checkpoint only checks for a stop. This replaces the whole `EeScheduler` (2,200 lines of seam, with the thread, semaphore, flag and alarm syscalls, which in `wotm.exe` would have to become "not supported" with a warning) to gain up to ~0.5 ms per frame. A cheap middle ground: take the clock off the checkpoint path with a host thread that sets `m_checkpointPending` at the vblank deadline.

   **Intermittent stall again:** in one of the three menu runs after this step, four consecutive stops of 0.15 to 1.2 s with little CPU (`[stall]` in `rtMain`, `inputUpdate`, `RtLoopView::startFrame` and `scePadGetState`, vblanks 2067 to 2070), right at the start of the fight; the other two runs, normal. The pcs are function entries without a native hook, and the capture locks (`wotm_live.inc`) are short. The tests run with the window minimized (`-WindowStyle Minimized`); it is worth checking whether the stall goes away with the window visible.

9. **IOP RAM out of the game executable** (done on 2026-10-19). By the call graph (`jal`), only the game's own movie decoder reaches the IOP memory: `sceSifAllocIopHeap` only has `strFileOpen` as a caller (from `CMovie::Play` and from the `initAll` of `MpegMovie`), `sceSifFreeIopHeap` only `strFileClose`, and `sendToIOP` (movie audio) sends through `sceSifSetDma`. The other SIF paths that reach `SetDma` (pad vibration, RPC, `sceSifResetIop`) are runtime stubs that do not touch the IOP memory. Measured in `wotm.exe` (temporary counter, already removed, on each access): with native movies, **no access** in the menu through the pad script up to the fight nor in a 4-monster fight. Without native movies, the game's `intro_m` allocates 160 KB in the IOP heap, writes the `.pss` blocks and stops there, because the decoder waits for the IPU. In other words, `wotm.exe` without native movies already did not get past the opening.

   **Done:** in `wotm.exe` native movies are the default (`main.cpp`: without `PS2X_FMV`, `PS2X_SKIP_MOVIES` or `PS2X_SKIP_CMOVIE`, it turns on `PS2X_FMV=1`), and the game's `IopSubsystem` (`ps2xIOP/src/iop_subsystem_host.cpp`) no longer has RAM or a heap: allocating, freeing, reading, writing and checking a range fail, with the warning `[iop] memoria do IOP pedida (...)` (IOP memory requested) the first 4 times. A second 2 MB block also leaves `wotm.exe`, the `iop_ram` of `PS2Memory` (`ps2_memory.cpp`), which was allocated and zeroed but had no reader in either executable. Checked: menu through the pad script up to the fight without `PS2X_FMV` (native movies turn on by themselves, the opening and the menu play) and 4-monster fight, no warning. `ps2EntryRunner.exe` does not change.

10. **EE scheduler replaced by a single-thread loop in the game executable** (done on 2026-10-19). With the inventory from step 8 (one thread, no INTC handler, one DMAC handler, the vblank), `wotm.exe` compiles another implementation of the same class (`ps2xRuntime/src/lib/Kernel/EeSchedulerGame.cpp`, instead of `EeScheduler.cpp`; the header and the game code do not change, except for new methods):
   - **The main thread runs directly.** There is no ready queue, time slice or thread switch. The checkpoint of the generated code (27 to 47 thousand per frame) only adds the cycles and checks an attention flag; it no longer reads the clock.
   - **The vblank comes from a host thread** with the 16.667 ms grid (rebuilt after a stall of more than 4 vblanks, as before). The EE applies it at the next checkpoint or in the wait: tick, CSR field bit, flag and tick of `SetVSyncFlag`, callback of `sceGsSyncVCallback`, INTC causes 2 and 3 (no handler in WotM).
   - **Waits in place.** `sceGsSyncV` (`WaitVSyncTick` in `Interrupt.cpp`, new method `waitVSyncHere`) sleeps until the vblank and returns to the caller with the result in `$v0`. Before, it threw a C++ exception (`EeDispatcherTransfer`) that unwound the stack up to the scheduler loop every frame, and the game came back through the pc. Semaphore, event flag, sleep and external wait also wait in place, serving vblanks and interrupts (WotM does not use them).
   - **Interrupts and callbacks run nested**, with each depth's own stack (the DMAC handler is delivered at the checkpoint following the end of the DMA, as before). What the header declares `[[noreturn]]` (`invokeCurrent`, `waitVSync` with continuation, `waitExternal`, `exitCurrent`) does the work in place and then throws the same exception, because the callers (RPC, syscall override, `ExitThread`, CD stream) count on it; none of these paths runs in WotM.
   - **Other threads do not exist.** `CreateThread` registers, `StartThread` fails, and so does `SetAlarm`, with the warning `[ee] ... nao suportado no wotm` (not supported in wotm). Measured: no warning in the menu or in the fight.
   - `WOTM_FIELDLOG` still works: the `[stall]` now comes from the vblank thread (three vblanks without the EE reaching a checkpoint or waiting), with the pc of the last call.
