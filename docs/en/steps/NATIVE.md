# Native layer (native/): drawing, textures, characters

(Docs index in [CLAUDE.md](../CLAUDE.md).) This file keeps **what is known**, not the diary of the investigations. The full account (discarded hypotheses, intermediate measurements) is in the earlier version: `git show 01050d2:docs/passos/NATIVO.md`.

## Overview, files and flow
The scene is read straight from EE RAM and drawn with raylib, without VU1/GS, using the game's camera. Files:
- `native/wotm_native.hpp` (single header: `Ram`, matrices, `decodeObject` = the `polyPkt` mesh, `Scene::collect/draw`, camera), `wotm_gs.hpp` (GS addressing, textures), `wotm_fx.hpp` (particles), `wotm_fmv.hpp` (movies), `wotm_snd.hpp` (sound), `viewer.cpp` (standalone viewer: free/game camera, `--shot`, `--texdump`, `--lod n`, `--cam`, `--disc`, `--rtx`), `fmvplay.cpp`, `build.bat` (MSVC; raylib from the runtime clone). Formats in [FORMATS.md](../FORMATS.md); offline mesh reader in `tools/ngp.py` (`TRACE` shows MSCAL/MSCNT per sub-packet).
- **Offline iteration (seconds):** the runtime writes `ram_<q>.bin` + `vram_<q>.bin` (`PS2X_DUMP_RAM="3300,3900"`) and `build\viewer.exe ram_<q>.bin` draws it. Dump of the open runtime: `python tools/pcsx2_auto/ramdump.py <discroot>/SCUS_971.97 saida.bin ps2EntryRunner` (the same script reads retail PCSX2).
- **Live:** `PS2X_SCENE=1` (with `PS2X_NO_VU1=1 PS2X_NO_VIF1=1 PS2X_NO_GS=1`) draws into a 4:3 render texture on top of the GS frame (`wotm_live.inc` -> `wotmDrawNative`); with no level loaded the GS frame continues. To run: `run_live.ps1` in the `wotm-recomp-win` clone (`-Auto 0` to play, `-Stats 1` logs `[native]`), or `WotM_Launcher.exe`. Keys: **F3** FPS counter (off at startup), **F11** toggles fullscreen and windowed, **F1** debug menu (cheats; "debug menu" section).
- **Rebuilding the runtime after touching `native/`:** `build_runtime.bat` at the root (or `tools/build_runtime.ps1`). Ninja **does not track** `native/*.hpp` or `native/runtime/*.inc` (they live outside the PS2Recomp tree): the script touches `ps2_runtime.cpp`; without that it prints "no work to do" and the game keeps the old drawing.
- **Addresses by name:** `native/wotm_syms.h`, generated by `python tools/native_syms.py --gen` from `symbol_addrs.txt`, provides `wotm::sym::<data>` and `wotm::fn::<function>` for the ELF's 7,282 symbols (gcc 2.95 names with `$`/`.` replaced by `_`; those starting with `_` or clashing with an MSVC macro get an `x` prefix). In new code, use the name, not the number; `--audit` lists what is still raw in `native/` (28 literals remain that are fields inside a symbol, whose correct name is the one from the types header, and ~40 that have no symbol: bss `D_*`, masks, VRAM addresses) and `--apply` replaces the exact ones. Regenerate the header when `symbol_addrs.txt` changes.
- **Where the runtime code lives:** the hooks and game-specific code that run inside the runtime are in **`native/runtime/`** in the repo: `wotm_live.inc` (live drawing, boot trace, watchdog, movies; includes `wotm_snd.inc`, `wotm_pad.inc` and `wotm_padsel.inc`: per-player controls and side selection), `wotm_scene.inc` (entry point included by `ps2_runtime.cpp`; includes `wotm_vu1check.inc`), `wotm_vu1check.inc` (VU1 vs native check, snapshot and `--vu1cmp`), `wotm_overrides.cpp` (game clock, `WOTM_MATCH`, `AIVSAI`...) and `wotm_vu0_native.cpp/.h` (dispatch of the VU0 microprograms; the translated `.gen.inc` goes to `<build>\wotm_gen`, outside the repo). The fork's CMake (`-DWOTM_NATIVE_DIR=<repo>/native`, mandatory) includes `native/` and `native/runtime/` and compiles both `.cpp` files. The patch `tools/runtime_patch/wotm-runtime.patch` holds only the PS2Recomp seams (CMake, `main.cpp`, taps in VIF1/VU1/memory, scheduler, pad, profiling). A change in `native/runtime/` is a normal commit in the repo; a change in a seam requires regenerating the patch.
- **Level change (`levelSignature`):** a hash of only the header of the level image at 0xA00000 (N + N pointers) and of `tempVramTexAddr`. The whole first KB does not work: it includes live nodes (the menu rewrites floats at +0x3E0..+0x3F8 during transitions), and with it the scene would be invalidated every frame (~870 meshes and ~80 textures reloaded, drawing taking 50-70 ms, screen at ~16/s during menu transitions). Diagnosis: `WOTM_CAMLOG=1` (one `[cam]` per draw).
- **Without VU1 nobody completes the packet:** the game waits for `objsInPacket | objsInAlphaPacket` (0x6F87A0/A4) to reach zero in `rtWaitForVu1` (hooked) and in a loop embedded in `particleDraw` (0x21B8A0); with `PS2X_NO_VU1` the presentation (60 Hz) zeroes both. Old experiment variables: `PS2X_GS_UPLOADS`, `PS2X_VIF1_UPLOADS`, `PS2X_NO_VU1=2` (no longer needed).

## Textures and palettes
- **Pixels:** `texInfo[texId]` (0x50F100, 16 B per entry) points to a packet: width `+0x24`, height `+0x26`, TBW `+0x2A`, PSM `+0x2B`, **linear** pixels starting at `+0x80` (T8 = 1 byte, T4 = 2 per byte, low nibble first). The `TBP0` of the object's TEX0 is usually 0 (`texm` patches it at draw time) and is not used.
- **Palettes come from the disc's `.RTX`**, never from the dump's VRAM (which holds menu leftovers). Entries of `(word0 >> 2) * 16` bytes, 16 B header (GS descriptor at `+8`: relative DBP in the halfword `+0xA`, TW/TH in bits 40..47); 16x16 CT32 = 256 colors (1040 B), 8x2 = 16 colors (80 B). `Scene::loadResources(ram, raiz)` indexes by **absolute CBP** (`rtxPal`); it is idempotent.
- **Base of each `.RTX`:** the game stacks level, players and AIs in load order; `fileStatus` (0x445390) holds `names[i][9]` (+0xB1) and `maxTexAddr[i]` (u16, +0x14C). Level base = `tempVramTexAddr (0x6F8818) >> 6`; base of file `i` = `maxTexAddr[i-1]`. Lookup: `LVL/<nome>.RTX`, `MON/<nome>.RTX`, `<nome>/<nome>.RTX` (menu: `SHELL/SHELL.RTX`) and `SHELL/<nome>.RTX` (LOAD, UI, SHELL2, PRESHELL).
- **CSM1:** 256-color CLUTs have bits 3 and 4 of the index swapped; logical entry `i` = word `(i & 0xE7) | ((i & 8) << 1) | ((i & 0x10) >> 1)`. Only in T8/T8H (without it: grainy portraits and monsters, without the yellow spikes).- **PSMT8H/4HL/4HH** (menu: screens, fonts, logos, 512x512 portraits): `texInfo` does not point to the right pixels; the pixels are in the `.RTX` (0x80 B header, psm in bits 32..37 of the desc, sizes `0x1080`, `0x880`, `0x40080`). `TEX0.TBP0 == DBP` of the entry; 4HL and 4HH share the DBP (the two nibbles of the same byte). Stored in `rtxImg[(psm<<16)|DBP]`. The entry with size 0 is the last in the file and also counts (in the monsters, the HUD portrait); in the monsters the DBP is relative and adds `fileStatus.maxResAddr` (+0x168) of the previous file, as in `texmResRelocate`. Texture 180 (128x128, tbp0 4096) comes from a file not yet identified.
- **Alpha:** texture and vertex go in **raw** (no `fixAlpha`, no ×4): the GS blends with As = At·Av/16384, and the `Scene::draw` shader does `3.969·t.a·v.a` (up to 255/128; in the common blend, As above 1 comes out in two extra passes, `gsBlendOver1/2` in `wotm_fx.hpp`) (CT24 and the CT16 bit give 0x80; untextured sections use `gsWhiteTexture`, alpha 0x80). Measurement and captures in [VU1CHECK.md](VU1CHECK.md), "Escala do alfa" (alpha scale). Object UVs = `int16/4096` normalized by size (as on retail; buildings go up to ±8 and repeat on purpose; UV outside 0..1 requires `TEXTURE_WRAP_REPEAT`).

## Meshes and draw state
- **Point lights:** fire (breath, `Weapons::CreateFire`, `Monster::lightOnFire`) creates lights in `pointLights` (0x6DFCE0: 32 `PointLight` of 0x40, position +0x10, range +0x1C, color +0x20, falloff +0x2C = range²/(16·intensity), enabled at +0x38). In pass 1 `hier` calls `GetClosestPts` (up to 8 enabled lights closest to the camera, for VU0 memory; with `closest[0] < 0` the count is 0 and the rest of `closest[]` keeps stale garbage). `hierTraverseAsm` calls VU0 program 0x748 for OBJECT with `pointLight` (0x80), `objType` 0 and, in a `_cs`, `ptLightMe` (+0xA9): with R = rows 0-2 of the matrix and T = row 3 minus the camera (camera-relative stack), v = Rᵀ(L − camera), it touches if |T + center − v|² < range² + radius², up to 3 lights, and sends T − v (q169-q171). With a light, `pktAddVu1ObjAsm` replaces the light program with 0x15D8 (before `dirLight`): color = min(255, color·q5 + Σ color_k·min(0.5, max(0, (L_k − p)·n)·falloff_k/|p − L_k|²)), n = normal/128, no directional light. `Scene::objectPointLights`/`pointRgb`; corpus snapshot `luz_pontual` (point light); check dump with the `ptl` line (q169-q175); `WOTM_PTLOG`.
- **Vertex alpha:** almost everything has ~0x42 and is opaque; VU1 sends it as is and the scale is the GS's (see "Alpha" above). The template's `PRIM.ABE` does not decide blending on its own; the shader does `discard` below ~6%.
- **ADC (STMASK + S-8):** skips only the triangle ending at that vertex; the strip continues. Treating it as a restart loses triangles (holes, torn sky). `tools/ngp.py` still uses the old model.
- **Multitexture:** up to 5 textures per object (`texId[5]` at `+0x50`, `numTextures` `+0x5A`, `gsTexCtx[i]` at `+0x70 + 0x30*i`). The 4th word (high REGS) of each section's GIF tag is the **selector `1 + 3*slot`**, with two rules: `sel = 0` **inherits** the previous section's texture (the GS keeps TEX0; state in `MeshData.curSlot`, initially 0), and **bit 15** is a flag (slot = `(sel & 0x7FFF)`). Without this: terrace with wall texture, "camouflaged" police cars (retail does not have these defects). Open, low risk: 1st section with `sel = 0` (only texId 189).
- **Blending:** the GS state of a translucent object comes from the **`ctx` of the nearest parent node that has one**: GROUP, TRANSLATE, ROTATE and SCALE at `+4`, ANIM_XFORM and ANIM_SCALE at `+8` (`Scene::CtxScope`); with none, `ctxGetDefaultGSCtx` (0x44). It is an A+D tag with `ALPHA_1` at `+0x20`, `TEST_1` and `ZBUF_1`. `0x44` = normal, `0x48` = additive (Kineticlops), `0x42` = `Cd - Cs*As`, `0x46` = `Cd*(1-As)` and `0x81` = `(Cd-Cs)*As` (Kineticlops in color 3). `Scene::groupState` reads the `ALPHA_1` byte (`DrawItem::blend`; `gsBlend` in `wotm_fx.hpp` translates any `(A-B)*C+D` into GL factors) and the `TEST_1` threshold (`DrawItem::aref`, shader uniform `alphaRef`; default `kGsAlphaRef` = alpha > 8, the common `0x8D`; ATE 0 or ATST ALWAYS = no test, `kGsAlphaNoTest`). The frame goes to the window **without blending**: the framebuffer alpha is the blends' alpha, not opacity. **Order:** outside the alpha OT (bit `0x8000` of the flags), opaque and translucent objects come out in traversal order, writing Z according to the `ZMSK` of the inherited `ZBUF_1` (`DrawItem::zmsk`); the alpha OT comes after, by depth band and LIFO (`alphaBin`, `inAlphaOT`), and shadows last ([VU1CHECK.md](VU1CHECK.md), "Ordem do hier e OT de alfa" (hier order and alpha OT)). `hierTraverseAsm` writes the current ctx into every object of the alpha OT, so the state does not leak from one object to the next (the explosion sphere's ctx comes from a TRANSLATE/ANIM, not from a GROUP; reading only GROUP it comes out with 0x44).
- **zBufferFudge** (`HierObject +0x28`, 1.0..1.12): **>1 = closer** (in the GS larger z is closer and z ~ 1/distance); native scales the vertex along the eye ray by `1/fz`. With the wrong direction, labels in the options menu, lit windows and dirt trails disappear.
- **Sky:** `worldCtx[0]` `+4/+8/+0xC` (`skyCs`, `skyCs2`, clouds), before the world, without depth, at `skyCs->trans` like `hierTraceSky` (not at the eye). `trans` only changes through `viewSetSkyTrans`, which `hierSetCamera` calls after the traversal passes a camera node: in the menus that is every frame (trans = eye); in a fight the sky stays where the last locator camera left it and the game camera moves around it (parallax of the mountain ring, `tex 108`; drawing the sky at the eye loses that parallax). It is included in the check's triangle comparison. **HUD:** ids 0x1C20..0x2133 (except button icons, below) are `hier` objects that the game places in front of the camera every frame (`Hud::update`, `Letterboxing::update`); they go to `Scene::hud`, drawn last, without depth (details in [VU1CHECK.md](VU1CHECK.md), "Corrigido" (fixed)). The HUD that comes out as a GS packet through `ScreenPolys` (the health marker of the other monsters) is read at the entry of `ScreenPolys::dmaData` (`wotm::readScreenPolys`) and drawn like the text, before it ([VU1CHECK.md](VU1CHECK.md), "Corrigido"); `Hud::dmaPacket` only exists with split screen, which native does not have.

## Hierarchy, LOD and characters
- **Rigid:** `CHAR_INSTANCE` (`+4` = `animOutput.val`, `+0xC` = `atMat`, `+0x14` = `animMatrixPtr`, `+0x18` = `animPktPtr`, children at `+0x2C`). `ANIM_XFORM` (op 17): the game computes the local matrix in `atMat[matrixIdx]` (`+0xC4`; `visible` float `+0xC`, children `+0xCC`); native only reads it.
- **Op 35:** container of `ANIM_XFORM` (count `+4`, children `+0xC`) with the monsters' **rigid parts** (hands, claws, head, thruster). Ignoring it removed Robo-47's hands and head and Togera's blades.
- **`ANIM_SCALE` (op 38):** visibility is `val[vidx]` (`vidx` int16 at `+0x10`): 0 skips the node and its children, `-1` = always. `+0xC` is static (reading it left Robo-47's blades and flame always visible).
- **`DESTRUCTIBLE` (op 39):** descends only into `child[whichChild].child`, with `whichChild` = `INTERACTIVE_STATE +4` of the parent. Validated in a match with attacks (building in ruins). Still missing: dust/fire/`Debris` and the `actions` of the state change. `WOTM_DESTRSTAT=1` counts per state.
- **`CONTROL` (op 8, "ghost" building):** `+4` solid, `+8` ghost version (or null = disappears), `+0xC numVolumes`, `+0xE volType`, sphere `+0x10/+0x1C`, BSP volumes at `+0x20` (leaf `0x200` = air). `volType == 0`: eye outside the air -> child2. `volType != 0`: segment eye -> sight point (`g_cameraLosPoints` 0x50F020, direction in xyz and distance in w; count at 0x50F0C0) crossing a solid leaf -> child2. `Scene::ctrlChild` reimplements it (the original `bspVecTestIn` is asm); only view 0 and up to 2 points.
- **LOD:** picks the highest index whose `switchOutDis` (`+0x20 + 16*i + 4`, squared distance) is larger than the squared distance from the center (`+0x10`, transformed) to the eye; none -> not drawn. Index 0 is the coarsest. With the level's `fade`, the cross-fade is the one from `hierTraverseAsm` (level i - 1 before i; `DrawItem::fade` and `lodX` take both to the alpha OT).
- **Skinned (monsters):** `CS` 96/97/101/105/106/107 -> GROUP -> `CHAR_INSTANCE` -> `SKEL_BONE` + `LOD`. The `polyPkt` is a **chain of sub-packets**: tag `0x600100b4` (bit 16 = skinned; the low 16 bits are not a size), `UNPACK V4-32 @0xB5` (up to 190 vertices: xyz + weight in w, **bone code in the low 8 bits of x, y and z**), normals `V3-8 @0x175`, strip sections; each sub-packet ends in two NOPs and the next one comes qword-aligned after zeros.
- **Matrix palette:** `animPktPtr[OBJECT+0x68]` (index of the OBJECT itself, as in `pktAddVu1ObjAsm`; negative = no palette, the game sends the packet at `+4`. It is not the LOD index: the Dragon has body and wings in the same LOD, at 5 and 6) -> 1st tag `3000007d <address>` -> block of 125 qwords (the Dragon's body uses its own palette of `0x41` qwords, 16 matrices, for the same VU1 address); bone code = qword address in VU1: `slot = (código & 0x7F) / 4`, matrix at `bloco + 0x10 + 0x40*slot`. `animMatrixPtr[i]` points to **shuffled** slots (do not use `animMatrixPtr[código/4]`). Bit 0x80 is not used by the microcode.
- **Weights (VU1 microcode disassembled with `tools/vu1dis.py`, output in `build/vu1/`, game code):** 3 bones per vertex, `w1 = w`, `w2 = frac(w * 2048)`, `w3 = 1 - w1 - w2`; position = `w1*Mx*p + w2*My*p + w3*Mz*p`. Implemented in `skinVertex`.
- **Robo-47:** the dome's **electric arc** is the `fx[]` of visual type 7 (VisArc), `texLoad[0]` 57; drawn by `Particles::arcQuads` (97.5% matched with VU1; [VU1CHECK.md](VU1CHECK.md), "Arco elétrico" (electric arc)).

## Physics with `dt = 1/updateRate` (runtime)
The game integrates several things with Euler using `dt = 1 / timerGetUpdateRate()` (0x2236D8). On retail the rate is 60 or 30; in the runtime it oscillated between 60 and 8 (vsyncs arrive in jerks: one game frame lasts 1 vsync, the next one 6), and with a large `dt` the integrators diverge:
- **Congar's fur "exploding":** the 8 fur bones (4, 8, 11, 13, 20, 22, 26, 28) are **springs** (`BoneSpring::update`, 0x11B5C0: `Spring::applyForces` + `PointMass::resolveForcesEuler`). The deviation of ~5 to 6 between `atMat.linha3` and `nó.t` on those bones is **normal** (the same on retail). The spring is only stable with `dt²·k/m` below ~4. Ruled out by measurement: the VU0 interpreter (15 million `vcallms` compared with the reference, `PS2X_VU0_VERIFY=1`), `vf0`, the native layer.
- **Monster spinning on its own (camera along with it):** `MonsterDynamics::updatePosition` (0x165100) integrates `ang.z` with damping ≈ `-40.5·velRot`, stable only with rate ≥ 21; at rate 10 the velocity reverses and grows. `WOTM_TURNLOG` prints `[turn]`.
- **Rate floor:** `timerGetUpdateRate` returns at least `WOTM_RATEMIN` (default 30; 0 disables) for the whole game (`wotm_overrides.cpp` in the runtime). On slow frames the game runs a little slower instead of skipping.
- **The `particleDraw` wait:** the game measures logic duration with timer 1 (`fields = ticks / 9619`, `updateRate = 60 / fields`). The `particleDraw` loop at 0x21B8A0 waits for `objsInPacket | objsInAlphaPacket` to reach zero (VU1 completion); without VU1, if only the presentation zeroed them, the loop would burn 32 virtual cycles per iteration and the game would measure 2 to 4 fields at random. That is why `main.cpp` (with `PS2X_NO_VU1`) and `EeScheduler::checkpointDue` zero the counters at the entry of `particleDraw` and do not count cycles in that loop.
- **Rate ceiling:** `timerWaitForMinUpdateRate` only waits one more vsync if the rate goes above the ceiling (`D_006F8DD8`, written by `timerInit`). With 1 and 2 players the ceiling is 60, and logic at 30 indicates runtime slowness. With 3 and 4 the game turns on "30 Hz mode" (`Shell::Use30HzMode`: `m_numPlayers >= 3`): `Shell::BootInitGame` calls `timerInit(30)` and `getVramAddr` switches the VRAM layout. The port changes only the `timerInit` at that point to 60 (`timerInit60` in `wotm_overrides.cpp`), and the logic with 3 and 4 players uses 60 whenever it fits in 1 field; `WOTM_30HZ=1` goes back to the ceiling of 30.
- **Fields = vblanks of the frame (`wotm_overrides.cpp`):** the frame starts a few host ms after the vblank, so the logic can cross a vblank with timer 1 below 1 field, and the game would count 1 field in a 2-vsync frame (the game runs slower than the clock). At the entry of `timerWaitForMinUpdateRate` the field counter is at least the number of vblanks since the start of the frame (marked by the `timerGetCurTics` called at its end or in `timerSetFrameStart`). The `particleDraw` wait also zeroes the counters inside the loop itself (they rise inside it).
- **Timer from the host clock (`wotm_overrides.cpp`; `WOTM_TIMER_EMU=1` goes back to the emulated timer 1):** `timerGetCurTics` is replaced entirely and returns the host clock at timer 1's frequency (576 kHz, BUSCLK/256, mode 0x82 of `timerInit`; 9619 ticks per field). `timer1Handler` keeps running, because it waits for vsync, but the fields it adds (`ceil(T1 / 9619)`, up to 16) come from host time since T1 was last zeroed (end of `timerWaitForMinUpdateRate`, `timerSetFrameStart` or the previous `timer1Handler`). The computation is done **at entry** and the emulated T1 is zeroed so the original adds 0: `timer1Handler` almost always blocks in `sceGsSyncV`, and resumption jumps straight into the middle of the recompiled function without going through the wrapper; an "after" in the wrapper does not run (this applies to any hook on a function that blocks). The rest of the timer (`timerSetFrameStart`, `timerEndOfRealTimeProcessing`, `timerGetFrameTime`, `timerGetAverageFrameTime`) only sees T1 through `timerGetCurTics`. The "fields = vblanks" rule still holds with the host clock: the delay between the vblank and the start of the frame (`wotmCaptureFrame` runs there) exists just the same. With both, game time keeps up with real time (`WOTM_FIELDLOG`), also with frames of 1 and 2 fields (`WOTM_LOGICDELAY`).
- **Vsync from the host clock (`EeScheduler.cpp` in the patch):** every scheduler deadline (vblank, alarm) expires only by the wall clock; the virtual clock is not pulled toward the wall clock and `waitForEvent` does not add delay. Virtual cycles remain for the EE timers and the time slice between threads; idle time adds the time actually spent stopped. Measurement and what remains open in [BOUNDARY.md](BOUNDARY.md), step 4. Test with slow frames: `WOTM_LOGICDELAY`.
- **VU0:** the interpreter (`VU1Interpreter` with a pipeline model) costs ~3.9 µs per `vcallms` and gives the same result as the upstream one: it does not zero the 64 KB XGKICK buffer on every call, commits only the queues with something ready, has `normalizeOperand`/`broadcast` inline and decodes the pair by reference. The offline bench re-runs the `PS2X_DUMP_VU0` samples and compares against the upstream interpreter.
- **Native VU0:** `tools/vu0native.py` reads the VU0 microcode from the ELF (VIF packet with MPG at file offset 0x15C890) and generates C++ for the 14 microprograms the game calls. The generated `.inc` is a translation of game code and stays outside the repo: `build_runtime.ps1` generates it in `ps2xRuntime/src/lib/vu/` when it is missing or when the script changes. `wotm_vu0_native.cpp` dispatches by pc and only uses the native version if the FNV-1a hash of the program's slice of code memory matches; the hash is recomputed when the code generation changes. `WOTM_VU0_INTERP=1` sends everything back to the interpreter, and `PS2X_VU0_VERIFY` and `PS2X_DUMP_VU0` also force it.
  - **Arithmetic:** the same as the interpreter, on all 4 lanes at once (SSE for float, AVX for double): normalized operands, float computation rounded toward zero and the result classified by its double value (zero, overflow, underflow), with the product's sticky bit in madd/msub.
  - **Branches and flags:** the generator compiles blocks specialized by the pipeline state at entry (cycles left until each VF/VI/ACC is ready, pending flags and where they are, VI saved for the next branch, `bal` return address). Stalls and the cycle at which each MAC/status flag becomes visible to `fmand`/`fsand` come from the state, without depending on the data. Branches become `goto`, and the 0x748 loop closes when the state repeats. 0x430 and 0x4D0 call subroutine 0x598 (sine and cosine with flag-based branches) and become 13 blocks each.
  - **Cross-check:** the cycle model matches the interpreter on the 11 straight-line programs. The interpreter's 4096-cycle budget, which cuts the program off in the middle, is not reproduced: native always runs to the end, like the hardware.
  - **Floating point:** the runtime compiles with `/fp:fast /arch:AVX2`, and with that the compiler fuses `acc + a*b` into an FMA, with a single rounding, while the VU rounds twice. The interpreter in the runtime therefore does not reproduce the VU bit for bit at that point. The native file compiles with `/fp:precise`, outside the unity batch.
  - **Bench:** in `vu0bench`, with native compiled as in the runtime, it is identical to the interpreter under `/fp:precise` across 840 thousand executions with perturbed inputs (extreme values, denormals, inf/nan, cancelling sums, random flags and VI), except those that exceed the budget. Against the samples recorded by the runtime there is a difference of 1 to 3 ulps, the same one the interpreter under `/fp:precise` has with them.
  - **Gain:** 13× to 28× per call (0x0: 3.5 → 0.15 µs; 0x1A8: 8.5 → 0.53 µs; 0x4D0: 11 → 0.58 µs).
  - **Automatic fight in Centro (1 vs 1):** CPU per frame dropped from median 15.0 / p90 18.6 / p99 23.4 ms to 4.7 / 6.3 / 10.0 ms. The logic stays at 60 in 99.9% of frames (before, 82%).
- **4 monsters (match in Centro: Shogun, 2 Congar, Lizard):** CPU per frame median/p90/p99 of 6.2/7.8/10.0 ms (21.2/25.4/28.3 with the interpreter); logic at 60 in almost every frame; game time 97% of real time. **Open:** host stalls of 100 to 330 ms outside the fight; `_NLG_Return2` (~12%, MSVC stack unwinding).
- **Reading `[field]`:** it is printed at the entry of `timerWaitForMinUpdateRate` (every frame) and describes the previous frame (`timerGetUpdateRate` does not work: in the menu and at the start of a level it is not called every frame, and the line would add up two). `syncv=N:ra,...` counts the calls to `sceGsSyncV`.
- **Recursion in PS2Recomp:** a recursive function paused at its call to itself cannot be treated as finished, or the game jumps to garbage; the handling is in `dispatchGuestBranch` (`ps2_runtime.cpp`). If it happens, the `[resume]` log lists the last 64 resumptions before the invalid pc.
- **Build:** the unity build does not recompile the batch that includes `main.cpp` when only that file changes; `tools/build_runtime.ps1` deletes that `.obj` on its own.

## Runtime: host hooks end with `pc = $ra`
Every hook of ours (sound, movies, `rtWaitForVu1`, `hierFlushObjQ`...) is registered with `hostLeaf<f>` (`ps2_runtime.h`): if the hook did not change `pc`, it does `pc = $ra`. Reason: when the time slice ends right at a call, the scheduler resumes by calling `lookupFunction(pc)`; recompiled functions and stubs end with `pc = $ra`, but a raw hook left `pc` at its own entry and was called forever (the logic froze while drawing stayed live; seen with `pc = snd_FlushSoundCommands`). A new hook without `hostLeaf` brings the freeze back. Open: `callGuest` (`wotm_snd.inc`) calls game code inside a hook and can be interrupted the same way. **Modal function:** the hooks' `callGuest` calls set `ra` to 0; a game function that runs frames and yields to the scheduler (`displayDialog`) is resumed by the scheduler without the host stack, and at the end returns to `pc` 0: the main thread becomes `Dormant` and the game freezes (the runtime logs `[resume] thread N terminou em pc 0` (thread N ended at pc 0) with the last resumptions). Rule: a game function that can wait for frames (dialogs, loads) does not go through `callGuest`; call it as a tail call (arguments in the registers, `pc` = the function, `ra` = the original caller's), like the end of round in `wotm_split4.inc`.

## Runtime: freeze and pace watchdog
On by default, in the presentation loop (`ps2_runtime.cpp`, next to `PS2X_DUMP_RAM`). `g_frame` (0x6F7E38) increments on every frame of the fight (`rtMain`) and of the menu (`ShellRtLoop::endField`, which also covers the pause dialog). If it stays still for `WOTM_WATCHDOG` seconds (default 8; 0 disables) while the screen keeps drawing, the logic has frozen. A movie (`movieIsPlaying`, 0x6F8650) does not count. This happens once per stop: `[vigia] CONGELOU` (watchdog: FROZE) lines with the EE threads (pc/ra to look up in `symbol_addrs.txt`) and the semaphores in `live.err.log`, plus `ram_vigia_<g_frame>.bin` and `vram_vigia_<g_frame>.bin` in the disc folder (`discroot`), which is the cwd. When the game moves again, `[vigia] g_frame voltou a andar` (g_frame is moving again) is printed. The legitimate stops measured (menu and level loads: `zipBuildHuffmanTable`, `Shell::FadeScreen`) last 1.3 to 2.5 s. Pace: 2 s windows with the game running below `WOTM_MINFPS` frames/s (default 25) produce `[vigia] LENTO` (SLOW) and then `ritmo normal de novo` (normal pace again) with the duration and the minimum, without a dump. Windows with a gap of more than 1 s between frames are loading and are left out.

## Runtime: debug menu (F1) and cheats
In a fight (only where native drawing runs), **F1** opens and closes the menu; with it open, **1** invincible, **2** stamina (normal, full, fury = 130), **3** special always ready, **4** CLOAK, **5** god mode (the game's own `m_godMode`, +0xE9: no damage, health, stamina and special full; plus, added by us, no hit reaction), **6** win the fight. Arrows and Enter belong to the pad, hence the numbers. When closed, an orange reminder shows what is on. The window only writes `g_wotmCheats` (`native/wotm_cheats.h`); the EE thread is what applies it, at the entry of `Monster::update` for each player (`m_monsters[0 .. m_numPlayers-1]`, `wotm_overrides.cpp`), before that player's logic for the frame.
- **Invincible:** `Monster::takeDamage` returns at entry when the victim is a player, including with forced damage. The hit still pushes (the reaction comes through another path); only health does not drop.
- **God mode without reaction:** on the player, `Monster::takeHit` (virtual entry of every hit), `knockBack` and `takeAdditiveRecoil` return at entry, and `enterNewState` refuses the reaction states (Recoil, KnockBack, Grappled, BeingSlammed, BeingThrown, Impaled, Stunned, Shocked, BigTakeHit, Countered), as the game does in mode 7. A building falling on top still kills (it stays that way, the owner's decision). Grabbing works in multiplayer with both players in god mode. Known and accepted: with both grabbing in the same frame, one of them can stay frozen after being thrown far away; turning god mode off and taking a hit brings it back to normal.
- **Win the fight:** `takeDamage(100000, force, jogador)` on each living AI (`m_monsters[4 + i]`, `i < m_numAIs`); the game follows its own flow (death, victory, round count). With bosses that are not a regular `Monster`, the effect is not known.
- **`WOTM_CHEATS=inv,stam|furia,esp,cloak,deus,vencer=N`** turns them on from the start; `vencer=N` (win=N) repeats the "win" every N seconds of game time (batch, advance on its own). Example for a batch: `WOTM_MATCH=3,1,1 WOTM_AIVSAI=1 WOTM_CHEATS=inv,esp,vencer=25`.

## Runtime: VU1 vs native check (`WOTM_VU1CHECK`)
Compares, per object and in numbers, what the VU1 microcode would send to the GS with what the native layer draws. It does not produce an image. Code in `wotm_vu1check.inc` (runtime); hooks in `ps2_memory.cpp` (origin of each chunk of the DMA chain), `ps2_vif1_interpreter.cpp` (origins up to each MSCAL/MSCNT), `ps2_vu1_core.cpp` (XGKICK output) and `main.cpp` (`hierFlushObjQ`).
- **How it works:** it runs in the usual native mode. VIF1 processes every chain that arrives (VU1 microcode and data kept up to date; without this only ~78% matched), but does not execute VU1 or feed the GS. Every `WOTM_VU1CHECK` seconds, on a fight frame (`g_frame` ≥ 30), `hierFlushObjQ` triggers the real DMA from the entry of `hier(0, 0)` to that of the next frame. Each XGKICK is broken down into triangles (strip orientation made equal to native's) and assigned to the native object whose `polyPkt` contains any of the origins of the chain chunks since the previous MSCAL. At the start of each chain, the native layer collects the scene with the RAM at that instant and projects with view 0's `worldToScreenMat` (`d = p - olho`, `X = l0·d`, `Y = l1·d`, `W = l3·d`, GS pixels centered at 2048). Each VU1 triangle matches the closest native one of the same object (vertices within 1 px). Only whole on-screen (640x224) and non-degenerate triangles are included.
- **Why collect per chain:** the chain references matrices and palettes in place (REF). Only the first packet goes out inside `hier`. At the end of pass 0, `hierCheckVifComplete` (0x2045A8, `bc0t`) says "busy" and the last packet, with the monsters, goes out through the DMA interrupt (`hierDmaHandler` → `hierFlushObjQ`), which the runtime delivers in the middle of the logic (`TheGame::Update`, `animationRunGlobal`). Collecting only at the entry of `hier`, monsters matched at 20% to 99%, depending on the frame. Answering "free" in `hierCheckVifComplete` sent the packet twice. The camera is copied into the packet, and a pass 0 chain can go out already inside pass 1. That is why native is projected with the camera at the entry of each pass and the one that matches best counts.
- **Back faces:** the microcode discards back faces in sections with bit 15 of the selector set (native does too, `Vtx::cull`; rule and exceptions in lead 11 of [VU1CHECK.md](VU1CHECK.md)). Those that VU1 draws through the clipping path match against the ones discarded by native and count as `costas pelo recorte` (back faces via clipping). When VU1 drew no back faces on an object, the leftover native ones count as `costas` (back faces), not as a difference.
- **Texture:** each matched pair compares the TEX0 in effect in the GS when VU1 drew (PACKED TEX0_1/TEX0_2 or A+D, between packets; context from `PRIM.CTXT`; `PRIM.TME` 0 = no texture) with the one of the section's slot in native (`texKey`/`objectTex0`). Only the fields that choose texels count (TBP0, TBW, PSM, TW, TH, CBP, CPSM, CSM, CSA).
- **Particles:** each system's packet lives inside its own `fx[i]` (`pkt` at +0), so the origin of the chain chunk tells the system. VU1 sends each particle as two triangles (pedestrians, stripes, type 7) or as a GS SPRITE (sprite, texSprite, debris, dust). The triangles become quads in pairs; native builds the same quads (`Particles::forEachQuad`, `Scene::spriteCorners` for debris), projected with the camera at the chain's instant or with one of the passes' (the one that matches best counts). Each quad matches if all corners are within 1 px. Output: the line `[vu1check] g=… particulas: sistemas, quadrados vu/nativo, casados %, SPRITE do GS (fora de `fx[]`), vértices não comparados (só pontos)` (particles: systems, vu/native quads, matched %, GS SPRITEs (outside `fx[]`), vertices not compared (points only)), the line `particulas por tipo (casados/vu/nativo)` (particles per type (matched/vu/native)) and up to 8 systems with the most difference (`fx`, preset, type, `n`, `sem pacote` (no packet)).
- **Particle color:** in matched quads, each VU1 corner (the vertex's RGBAQ; for SPRITE, that of the 2nd vertex) against the closest native corner, with the color the drawing uses (`Particles::forEachQuadColored`, which shares `quadColor` with `drawSystem`; debris: `Sprite::gsCol`). Line `particulas cor: casados com cor | cor difere (RGB > 4) | alfa difere (> 4) | por tipo (cor/alfa/casados)` (particle color: matched with color | color differs | alpha differs | per type (color/alpha/matched)) and up to 6 systems with the 1st difference (VU1 and native RGBA).
- **Lines:** XGKICK PRIM 1/2 (only `FX_LINE` uses them) against native (`pos` → `pos − vel`, the particle's color and alpha 0 at the tail). Matches both ends within 1 px; `so a ponta casa` (only the tip matches) = the particle's end matches and the other does not. Line `linhas: XGKICK N segmentos (fora de fx[]) | vu, nativo, casados | cor/alfa difere` (lines: XGKICK N segments (outside fx[]) | vu, native, matched | color/alpha differs); dump `line,vu|nat`, `linecam`, `linemat`, `linep`.
- **Fans:** PRIM 5 becomes triangles (1st, second-to-last, last vertex) and enters the comparison like the rest. In the corpus they all come from the microprogram's clipping and cross the screen edge (they count under `fora da tela` (off screen)).
- **Texels (only in `--vu1cmp` with images):** each XGKICK TEX0 is read from GS VRAM at draw time, the way the GS samples it (`decodeVram`: CT32/24/16, T8, T4, T8H/T4HL/T4HH; CSM1 palette through GS addressing), and compared, in matched triangles with the same texture, with what native decodes (`Scene::decodeTex`, raw alpha). RGB always, alpha only with TCC = 1. Line `texels: pares textura x objeto | iguais (<= 1), perto (<= 8), diferem, tamanho difere, VRAM com outra textura do mesmo TBP | uploads no quadro` (texels: texture x object pairs | equal, close, differ, size differs, VRAM with another texture at the same TBP | uploads in the frame) and up to 6 worst (`texels tex <id>`). In a fight no texture is uploaded within the frame: they are already in the snapshot's VRAM.
- **Output:** per check, one line `[vu1check] g=… objetos vu/nativo/ambos | tris vu (repetidos: o mesmo triângulo redesenhado, como a sombra projetada) /nativo, casados % (sem os repetidos), faltam (do VU1, sem par nativo), sobram (do nativo, sem par) (costas) | textura difere, sem TEX0 | XGKICK (todos os triângulos do VU1), fora da tela | sem objeto, cadeias, tempo da coleta, …, VIF1 fora de passo` (objects vu/native/both | vu tris (repeated: the same triangle redrawn, like the projected shadow) /native, matched % (excluding repeats), missing (from VU1, with no native pair), extra (from native, with no pair) (back faces) | texture differs, no TEX0 | XGKICK (all VU1 triangles), off screen | no object, chains, collection time, ..., VIF1 out of step) (invalid VIF1 codes since boot; nonzero = VIF1 read data as commands, see [VU1CHECK.md](VU1CHECK.md)). Then come up to 8 objects with the most geometry difference (`pkt`, `no`, `tex`, skinned, items), up to 8 with a different texture (`textura pkt`, with the most common TEX0 pair) and the origins of VU1 triangles with no native object. Collection costs 20 to 100 ms on one frame every N s. With `WOTM_VU1CHECK_DUMP=<prefixo>`, each check writes all triangles to `<prefixo>_<g_frame>.csv` for analysis (last column: TEX0).
- **Status and open leads:** in [VU1CHECK.md](VU1CHECK.md) (single source; do not duplicate here). References to "Corrigido" (fixed) entries (here and in the code) are in the history: `git show 5eca44b:docs/passos/VU1CHECK.md`.
- **Snapshot and check without the game:** `WOTM_VU1CHECK_SNAP=<prefixo>` writes the session's sampled frames into a single file, `<prefixo>_<g_frame do primeiro>.vu1snap` (g_frame of the first one): in the first, the VU1/VIF1 state and the whole RAM and VRAM at the entry of `hier(0,0)` (~36 MB); in the following ones, the state and only the 4 KB pages that changed (~7 MB per frame in a fight). Within each frame, in the order they happened, each DMA chain (pages that changed, chunk origins and the bytes) and the entry of `hier(0,1)`. What VU1 sends to the GS is a function of only that (VIF1 reads the copy of the chain, never RAM). `WOTM_VU1CHECK_SNAP_MAX=<MB>` (default 2048) stops writing at the ceiling. **Trigger, burst and shot limit:** `WOTM_VU1CHECK_WHEN=fx:<tipo>|preset:<fxId>|frame:<a>-<b>[,...]` only samples when the condition **becomes true** (edge: the event was born; a permanent emitter, such as the volcano smoke, fires once, an explosion fires on each new explosion). `fx:` is the visual type, `preset:` is the system's `fxId` (names in `tools/fx.py`) and separates the volcano smoke from a building's; the `WOTM_VU1CHECK` period becomes the minimum rest between shots. `WOTM_VU1CHECK_BURST=<k>` samples `k` consecutive frames per shot and `WOTM_VU1CHECK_SHOTS=<n>` limits the session's shots. To see a rare event, you do not wait for the clock: you provoke the event (`WOTM_MATCH`, `PS2X_PAD`) and record the burst when it appears. With the snapshot on, the runtime turns on `PS2X_GS_UPLOADS=1` by itself: texture and CLUT uploads reach the GS (without rasterizing), so the file's VRAM has the textures the reference image needs. It also intercepts `texmActivateTexture` (a miss in the level's texture cache): outside the sampled frame the `hier` chain does not go to DMA, and the swapped texture's upload would ride in it; the hook sends the upload packet straight to the GS (the mipmaps of `texmSetMipMapTbl` are left out). Snapshots recorded without that hook have the old texture in those slots. `tools\vu1cmp.ps1 <arquivo ou pasta> [-Frame <g_frame>] [-Dump <prefixo>] [-Full] [-NoPng]` (file or folder) runs `ps2EntryRunner --vu1cmp <arquivo>...` (one execution for all files: opening the runtime, with window and audio, costs more than the comparison; GS, VU1, the native presentation and the lens flares restart from scratch for each file, and the output and images are the same as with one process per file): it opens the runtime without the game, restores the state, reapplies the chains with the same native collection and prints the same `[vu1check]` output for each frame (the live check's, apart from collection time; seconds per session). A frame cut off by the process dying is ignored with a warning; the previous ones count. The replay runs on a thread with a 512 MB stack: the main thread overflows. **Images** (default; `-NoPng` disables), next to the file, `<arquivo>_<g_frame>_{ref,nat,diff,trio}.png` at 640x448: `ref` is the runtime's software GS fed with the same packets (XGKICK, PATH2 and the frame's GIF channel), **an approximation of the PS2 GS, not the GS**: it guides the eye, the criterion is still the table; `nat` is the native layer through the same function as the live game, with the RAM at the frame's entry and without the FPS counter; `diff` marks in red the pixels that differ by more than 24 in a channel, over the darkened reference; `trio` is the three side by side. Expected differences: the `ScreenPolys` health marker, which the runtime's GS does not paint (PCSX2 does), the sky (GS gradient/dither) and the passes' camera. For the runtime's GS to draw the frame, the replay does a warm-up (runs the frame once through the GS only, restores VRAM and VU1 to the entry state, reapplies the GIF channel packets, which clear Z, and forces FRAME to this frame's buffer, because the frame's drawing environment was sent in the previous window). It serves as a regression corpus: a folder of sessions named after what they show, run in full after each change in `native/`. Delete the sessions once the fix is validated (rule in [CLAUDE.md](../CLAUDE.md)).
- **Out of scope:** vertex color, blending and alpha (the opaque explosion); VU1 lines (`line`) and fans are only counted.
- **Full emulated path (without `PS2X_NO_VU1`):** the fight stopped on the first frame (the `particleDraw` loop) and, with that loop released, crashed in `GS::consumeLocalToHostBytes` (VRAM read from `sceGsExecStoreImage`, called every frame from 0x2153FC). The check does not use that path. To locate a `[CRASH] exe+0x…`: relink with `/MAP` (`set _LINK_=/MAP:<arquivo>`, delete the exe and run `build_dev.bat`) and look for the largest symbol ≤ the address.

## Lessons on method
- **An object half disappears and the wireframe is whole: suspect render state before geometry.** The enemy monster's "holes" were culling turned back on before the flush of the last batch (the GL state applies at flush time): flush (`rlEnd(); rlDrawRenderBatchActive();`) before changing state. A long hunt through palette, weights and pose found nothing because mesh, palette and matrix were correct.
- raylib: `rlBegin` with a different mode resets the texture (call it before `rlSetTexture`), and flush the batch on every texture change.
- `WOTM_NOSKIN` is not a reference pose (positions are local to the bone); `WOTM_ONLYTEX` on its own removes body parts and creates false holed silhouettes.
- `getenv` inside the `drawList` vertex loop brings the menu down to ~1.6 FPS.
- A retail dump from PCSX2 brings the geometry, but the texture pixels have already been reused; since `texInfo` is identical between retail and runtime, copying the pixel packets from the runtime dump gives a textured **hybrid dump** in the retail pose.

## Movies (FMV)
- **Cut:** the game's decoder (SCE's "ezmpeg" sample, IPU via DMA) depends on the IPU, which the runtime does not emulate. `native/wotm_fmv.hpp` replaces `playMpegMovieWithDB` (0x20F4B0) and `updateMpegMovieDecoding` (0x20F540) for the fullscreen ones (at the end: `movieRequested` 0, `movieIsPlaying` 0, `movieIsCompletelyFinished` 1) and `CMovie::Play/Update/End` (0x210090/0x210408/0x210360) for the movie on the menu's big screen (`mov/sheldemo.pss`, looping). `Update` redoes `moviesSetScreenObject`: the big-screen object gets texId 999 (TEX0 CT32 at 0x3BA0, 256x128), which `Scene` replaces with the player's texture.
- **Format:** video 0xE0 (MPEG-2 via `libavcodec`, BT.601), audio in private stream 0xBD (`SShd`/`SSbd`, 16-bit PCM 48 kHz stereo in blocks of 512 bytes per channel, which FFmpeg does not recognize). [FORMATS.md](../FORMATS.md) ("Filmes .PSS" (.PSS movies)), `tools/pss.py`.
- **Runtime:** `PS2X_FMV=1` (`wotmFmvInstall`; takes precedence over `PS2X_SKIP_MOVIES`/`SKIP_CMOVIE`; in `wotm.exe` it turns on by itself if none of the three is defined, [BOUNDARY](BOUNDARY.md) step 9); `.PSS` from the disc folder or the ISO (`PS2X_CD_IMAGE`; `WOTM_DISC`/`WOTM_ISO` force it), `WOTM_FMV_MUTE=1`. Skip: Space/Enter/cross/start (`skip_` -> `continuar = 0`), from the raylib keyboard/gamepad or from the pad the game reads (`inputPadData`, a new press of X/Start: works for the `PS2X_PAD` script), without the 600-frame wait that `uiMain` imposes on `intro_m`; the "Sony presents" and "trademark" screens are the first ~10 s of `intro_m.pss`.
- **Pitfall fixed:** `Movie::close` must zero the L/R pair being assembled (`blk_`), otherwise the next movie comes out with hiss.
- **Missing:** the audio follows the wall clock, not the game's; the blocking `playMpegMovie` (0x20F440, no caller) was left out.

## Camera and snapshot
- **Camera:** `worldToScreenMat` embeds the axes (row 0 = 384·right + 2048·forward, row 1 = −180.48·up + 2048·forward, row 3 = forward; in the menu the horizontal focal length is 496). The vertical FOV comes from the matrix itself (63.6° in gameplay); do not mix it with the `_cs` read at another instant. **The eye comes from `worldCtx[view].eo`** (+0x20, = −`cs->trans`), which `viewUpdate` writes together with the matrix, and forward and up come from the matrix itself. The `_cs` only serves as a fallback in the menu. In the fight intro (the camera rising along the building), the game puts another camera into the same `_cs` (0x800d30) for an instant in the middle of the frame. The matrix still has the right one. The native read caught that instant, sometimes halfway (x and y from one camera, z from the other), and the screen cut for one frame to another corner of the map: 14 times in 50 s with the raw `_cs`, none with `eo`. The `[cam]` of `WOTM_CAMLOG` includes `cs=` (pointers of views 0 and 1), `wm3=` (the matrix's forward), `csp=`/`csu=` (position and up of the `_cs`).
- **Presentation rate (`wotm_live.inc`, `initPresentRate`):** the window presents at the monitor's rate (`GetMonitorRefreshRate`; `WOTM_HZ=<n>` fixes it) with vsync (`WOTM_VSYNC=0` disables it), in place of the fixed `SetTargetFPS(60)` of `ps2_runtime.cpp`. The game logic stays at 60, so the scene is only **redrawn** when a new snapshot arrives (or when the `Shell::FadeScreen` fade changes, with the free camera paused, with the window resized, or at ~60/s if no frame has arrived for 40 ms: pause and loops without capture); in the other presentations the last image is just presented again. The cost stays that of 60, and texId 0 (previous frame) is still the previous drawing. On a 180 Hz monitor that is ~176 presentations and ~60 redraws per second (`docs/screenshots/2026-10-18/2026-10-18_apresentacao_180hz_luta.png`). `PS2X_STATS` shows `redesenhos=` (redraws) on the `[native]` line and, every 300 presentations, the average time of each redraw with 1 and 2 views (wall and CPU of the window thread; `[native] redesenho:` (redraw)). The runtime's per-presentation counters (`PS2X_SHOT_FRAMES`, `PS2X_COVERAGE` every 300, `PS2X_DUMP_RAM`) count presentations, which are 3 per game frame on a 180 Hz monitor. **Frame interpolation** (INTERPOLATE FRAMES option, `WOTM_INTERP`, on by default; table below): it applies with presentation above 60 Hz, or up to 60 with the game at 30 (half or more of the last 64 frames with a 2-field gap turns it on, 1/8 or less turns it off; with the game at 60 it would only add one frame of delay). If the redraw does not fit in the presentation period (moving average of the redraw block's time, `g_drawMs`, each sample capped at two periods, above 85% of the period), the blending is suspended and comes back below 60%, with an `[interp]` line in the log: with vsync dropping to half, the screen would be worse than without it. With it on, every presentation redraws the blend of the last two snapshots (`Scene::showBlend`): items matched by `(cs, node, occurrence)`, matrix decomposed into per-row scale, rotation (slerp) and translation; bone palette bone by bone; camera with linear position and FOV and axes by nlerp; a camera cut (400 units, `dot(forward) < 0.7`, FOV changing by more than 5°, another view) shows the newest frame; HUD, icons and the high-priority list go to the blended camera by their position relative to the newest frame's camera. The displayed instant follows a clock in fields (`Snapshot::fields`, the counter at the start of the frame, and `Snapshot::hostT`, the capture time; the offset between the two is filtered at 5% per frame), one game frame behind the newest one plus a 3 ms margin; when the new frame arrives early, the blend is that of the previous pair (`State::prev2`). The capture culls by sphere with a radius 1.2 times larger (`Scene::cullMargin`), so the delayed view does not lose objects at the edge. Cost: one redraw per presentation (at 180 Hz, ~2.5 ms with 1 view and ~4.6 with 2) and +1 frame of delay. **Particles and debris** step back from the newest frame by their own velocity, `(1 − α)` of one `particleMove` step (`Particles::stepBack`: `pos_B − pos_A = f·(vel_B + vento − (0, 0, gravidade·f))` over `f` fields; wind with the `Gusts` gusts; no gravity for dust, wake and kite; z locked for wake and kite on the water): the first `n − newParticles` of each system, because the ones at the end were born in that step and stay where they are. `Particles::blendRam` builds, in a shadow copy of the `Scene` (`fxMix_`), B's ranges with the stepped-back positions, and writes into it the `worldToScreenMat` and the eye (`worldCtx.eo`) of the blended camera (`M' = M_B·C_Bᵀ·C_I` in columns 0-2, C = camera axes), which the strite, the line and the fog read. Debris (`Sprite`) stores the step at collection (`Sprite::step`, `Sprite::grav`). Size (`pos.w`), age and color stay those of B. Arcs, sprine, chain and trail (points placed by the game) and the emitter's movement (fire attached to the monster) do not step back. **2D attached to 3D:** the lens flare, which the game projected with B's camera, is unprojected with it (by the W depth; the one at infinity only by direction) and projected with the blended one (`Scene::blendFlares`; W and the GS Z redone, whatever leaves the screen or falls behind the camera disappears). The focal length comes from the view's `worldToScreenMat` in the shadow copy, scaled by the blended FOV. Bars over the enemy and the health icon (`Scene::blendAnchors`, `anchorShift`) follow the annotated world point (`HudAnchor`), matched with the nearest icon in A (same view, up to 100 units): if the icon is at the same distance from the point's projection in A and in B, the blended point goes through the blended camera; if not (the game clamped it to the screen edge), it blends the screen position. In split screen the presentation loop does this view by view on a copy of the bars, the game's icon (polygons of the whole window) and the flares. The fades' alpha blends with A's when the rectangle (place, color, texture) is the same. Text and `Shell::FadeScreen` (loop without capture) stay those of the newest frame. **Attached to the camera outside the HUD lists** (menu panels, view-aligned objects): the matched object whose pose relative to the camera is the same in A and in B goes with the blended camera, like the HUD, instead of blending the matrix in the world. **Cut:** a view that appears or disappears (split screen turning on, the grab's unified view) has no pair and comes out as B. **texId 0** (video environment map, CLOAK) reads the previous presentation, closer in time than the game's previous frame. The launcher detects the main monitor's resolution and rate (current mode, in real pixels) and, with no saved configuration, suggests the largest resolution that fits it.

## Text and menu buttons
- **Text:** comes from the font hooks (`wotm::FontText` in `wotm_native.hpp`; hooks in `wotm_overrides.cpp`): `fontInitPacket` (TEX0 of the boot atlas), `fontSetTexId` (atlas from the `.RTX`), `fontSetColorGifTag` (color; with the packet empty it rewrites the header color, which applies at the start of the next frame), `fontBuildPrim` (one glyph, with the same computation as the original from `fonts[2]` and the current view's `viewDef`) and `fontDmaFontData` (closes the frame). The `ScreenPolys` HUD comes the same way, through the `polyBuildPrim` hook (`wotm::screenPolyFromCall`: `resolveFX` and the sprite redone from the arguments, identical to the packet); the replay reads `s_polyBuffer` (`readScreenPolys`). Packet format: A+D tag (`TEX0_1` = PSMT8H 512x512 atlas), `[PRIM,RGBAQ]` + color, `[UV,XYZ3,UV,XYZ2]` with `NLOOP` sprites (12.4). 640x224 screen: `x - 1728`, `y - 1936` (split screen not handled yet). Color: the GS does texture·color/0x80 and saturates, so the shader doubles the RGB.
- **Button icons:** `CS` from the `McButtons` pool (ids `0x1F51..0x1F54`, `0x240E..0x2411`) placed by `AlignCsWithView` ~80 units in front of the camera; they ended up below the drive-in floor. They go to `Scene::overlay`, drawn last without depth. **Fade:** `screenSetButtonAlpha` copies `targetAlpha` to `+0x4C` of the child object; `drawList(..., fadeByNode=true)` multiplies the alpha by that float.
- **Fades:** the game darkens the screen with an untextured GS SPRITE (ABE, `ALPHA_1` 0x44, color over the whole view, alpha 0x80 = covers) built on the spot: `rtFadeScreen` (fight entry, alpha 0x80 − 2·g_frame), `TheGame::updateFadeOut`/`updateFadeOutAndIn` (end of round, cinemas, camera change) put the packet in the `gsPkt` queue; `uiFadeScreen` (menu entry) builds it on the stack and sends it directly; `Shell::FadeScreen` (menu → level, end of loading) is its own loop that waits for vsyncs. Native rebuilds the rectangle from the arguments, without reading a packet (hooks in `wotm_overrides.cpp`, computation in `wotm_live.inc` with `wotm::viewFadeRect`): `rtFadeScreen(vista, quanto)` and `uiFadeScreen(quanto)` (view, amount) give alpha 0x80 − amount over the whole view; `TheGame` is read on return from `updateFadeOut`/`updateFadeOutAndIn` (level at `+0x120450`, one view per player, only view 0 with a movie or a single view); the list goes in the snapshot (`Snapshot::screenRects`). `Shell::FadeScreen` does not go through the capture: the entry stores view, color, start, end and step, and each `sceGsSyncV` of the loop advances the alpha (`wotmShellFadeStep`/`wotmShellFadeStepDone`); the presentation uses that alpha until the next capture. With `b = false` it does not redraw the scene and repaints the fade over the same buffer every field, so the darkening accumulates (Π(1 − a/128) over that buffer's alphas) and native draws the equivalent alpha. `Scene::drawScreenRects` draws after the text; a rectangle as wide as the screen covers the whole window (widescreen), a smaller one stays in the 4:3 strip. Photo: `docs/screenshots/2026-10-16/2026-10-16_fades_menu_e_entrada_da_fase.png`; the VU1 vs native check does not see the fades (replay without the hooks). **Level load:** after `Shell::LoadLevelFiles` puts the new level in RAM, `loadResources` swaps the textures for the level's, and the `LOAD` card, if redrawn, would come out with some arbitrary texture of the level (a "green sphere" on the loading screen, in CENTRAL the power-up glow, and a green, red or white light in the center of the screen at match entry, depending on the level). On the PS2 the screen stays frozen on the card's last frame: the load bar is drawn directly into the frame, without `hier`, and the `FadeScreen(0, false, ...)` after `FinishLoadBar` only darkens that image. That is why, from the entry of `LoadLevelFiles` to the entry of `rtMain` (hooks in `wotm_overrides.cpp`, `wotmLoadFreeze`), the capture publishes nothing and the presentation repeats the last drawn frame, with the `Shell::FadeScreen` fade on top. The load bar still does not appear (it does not go through native drawing). The card's fade-in (the `FadeScreen` with the `DisplayLoadBackground` redraw, which does `hier(0, 0)` and `sceGsSyncV` per step, without `timerWaitForMinUpdateRate`) does not go through the normal capture: the `sceGsSyncV` hook recognizes the loop's two return addresses and publishes the step's scene without turning off the fade (`wotmCaptureFadeStep`).
- **Menu black bars:** in the menu the cinema bars are not the HUD's `Letterboxing` (that one is for the cinemas and intros of story mode) but `letterboxDmaData(alfa)`, which `userintMain` calls between `hier(0,0)` and `hier(0,1)`: two black 24-line SPRITEs at the top and bottom of the view, alpha `alfa·128`, without A+D (it uses the `ALPHA_1` 0x44 in effect). Rebuilt at entry from the alpha in `$f12` (`wotmLetterbox`) and drawn with the `underText` rectangles: after the scene, before the high-priority list and the text. They cover the width of the view, so in widescreen they span the window from side to side.
- Old menu pending items, not rechecked after the fixes: logo and "player 1" without color, dark and grainy cars (maybe reflection maps), wooden lattice with dotted alpha (texId 166; probably original).

## Projected shadows
- **Retail (`common/ps`):** up to 10 blockers in `psBlkLst` (0x51C600, 0x30 B: `cs` +0x10, second `cs` +0x18, radius +0x20, factor +0x24 (9), range² +0x28 (1200²), in-use u16 +0x2E; `psBlockerAdd`), drawn from the light's direction (`psLitDirWs`, 0x54CC90; view 4) into a small texture, filtered and reprojected onto nearby objects. Active if `psSetShadowOnOff` (0x6F8D7C), `cs->drawMe` and the view's bit in `cs+0xE`. Intensity `psShadowIntens` (0x6F8820) = 80.
- **Native:** `Scene::collectShadows`/`drawShadows`: only objects without `dontCastShadow` (bit 29 of the OBJECT bits at +0xC; `psBldBlkRObjs` skips them: on Kineticlops only the eye casts) enter the silhouette, rasterized on the CPU (128x128, orthographic, half side `raio * 1.1` (radius), two 3x3 box passes) and reprojected onto the objects whose sphere crosses the shadow cylinder. Differences: orthographic (retail: perspective with `psZoomT`), approximate filter, silhouette LOD. **Validated only with a synthetic scene.** The silhouette uses the `hierShadow` LOD (fixed blocker distance, `psBlkLst + 0x28`) and is not culled by the view; it is reused between redraws (same inputs) and between the split screen views (tolerance of 1.5 units), and uses the snapshot's palette (`forEachTriPos`).

## 64 MB RAM and loading above 32 MB
- **The runtime has 64 MB and the game sees 32.** In the runtime patch (`ps2_memory.h`): `PS2_RAM_SIZE` 64 MB and `PS2_GUEST_RAM_SIZE` 32 MB. The
  main thread's stack (`SetupThread` with stack -1), `GetMemorySize`, the runtime heap and the stack of the asynchronous callbacks
  follow the second (`System.cpp`, `ps2_runtime.cpp/.h`), so everything the game allocates lands where it would on the PS2; the upper 32 MB only
  receive what the hooks send there. Addressing is by mask (`PS2_RAM_MASK`). Applies to both executables.
- **Monster loading** (`wotm_overrides.cpp`, `loadMonstersDBHigh`): at the entry of `Shell::LoadMonstersDB` the next load
  address (`fileStatus.ngpAddr[ngpLoaded]`, right after the level's NGP) becomes 0x2000000. The monsters' NGPs and, behind them, the RTX and TEX
  of the level and of the monsters go up; only the level's NGP stays below. The relocation (`dbsRelocateViaPtrListFile`) adds "address -
  0xA00000" in 32 bits and works at any address. `WOTM_HIGHRAM=0` goes back to the PS2's contiguous loading (with 8 monsters, Metro goes past
  32 MB and freezes). The line `[wotm] carga da fase` (level load) says how much is left until the end of RAM, and `N de 1000 texIds` (N of 1000 texIds) warns near the ceiling of
  `texInfo`.
- 32 MB snapshots still open: the replay accepts RAM smaller than the build's and zeroes the rest.

## Save in JSON (`wotm_save.inc`, `wotm_json.hpp`)
Format of the card binaries: [FORMATS.md](../FORMATS.md), "Save do memory card" (memory card save). `WOTM_SAVEJSON=0` turns it off (only `mc0/`/`mc1/`).
- **Hooks:** at the entry of `MonsterMc::stdInit` and `MonsterMc::stdExit`, which open and close every sequence of card pages.
  In `stdInit` the binaries of both cards are rebuilt from `save.json`; in `stdExit`, if the game wrote any binary (date or
  size changed), the JSON is updated from it. The game sees the same 0x380/0x280 bytes; the stack garbage (0xF4 onward, except the
  mark) becomes zero.
- **A single JSON**, next to the card folder (`discroot/save.json`): `options`, `battleTokens`, `unlocks` (monsters and costumes, levels),
  `records.enduranceBest` (`easy`/`medium`/`hard`) and `unknown` (the unnamed fields), once for both cards; `saves` with up to 99
  slots (`null` = empty; the array ends at the last occupied one). Card 1's `savegame.dat` holds slots 0 to 9 and card 2's holds 10 to 19; the
  others exist only in the JSON. Keys by name (`"congar": {"skins": [...]}`, `"levels": {"ufo": true}`, level and monster of the saves by
  name), never by index: a mod that adds a monster or skin only adds keys. Keys the code does not know stay in the file
  when it is rewritten. `unlocks.mechaSweetTooth` takes precedence over `agamo.skins[3]` (created with the card's state when missing). The
  old `unknown.game1204B0` is still read and dropped on rewrite.
- **Adventure costume by name:** the slot stores `"costume": "ultra-v/roxo"`; a single `resolveCostume` serves `jsonToAdventure`, the
  save list and the 3D monster. Missing skin: costume 0, a log line and "skin missing" in the list; saving the same adventure returns the name to the JSON
  (forgotten when a monster selection screen opens). `adventureToJson` leaves alone a slot that says the same as the binary.
- **Migration:** with no JSON, the first `stdInit` creates it from the cards; with a JSON lacking the slots of a card that has adventures, they
  are imported. A JSON that does not open is reported in the log, the cards stay as they are, and before the game rewrites it the user's file
  goes to `save.json.bad`. Writing is by temporary file and swap. The `[wotm] save: no jogo, N tokens, dificuldade D` (save: in the game, N tokens, difficulty D) at the end of
  each sequence says what the game has in RAM.
- **Autosave** (always on): the six `MonsterMc::update*` that are not from the adventure (`BootLoad`,
  `SettingsLoad`, `SettingsSave`, `UnlockSave`, `EndOfStorySave`, `EndureSave`) become a direct copy (the same as `getSettingsData`/
  `setSettingsData`) between RAM and `save.json`, which sets `+0`, `+4` and `McPageMgr+0x130` (sequence finished: the options screen only
  comes back with it) in the same call. The callers only repeat the `update*` until `MonsterMc+4`. The swap keeps the unlock screen's purchase
  inside the save (like `McSaveSettings::update`), and the boot still normalizes mono and applies volume and vibration in the
  caller. The tokens the game adds outside the sequences (end of a story level) are caught by a watchdog in `sceGsSyncV`: tokens or
  unlocks different from the last save go to the JSON (only those: the options menu may hold values not yet accepted). The end of
  endurance saves the larger of the record and the monsters defeated by player 1, in RAM and in the JSON (`[wotm] save: recorde do endurance (medium): 0 -> 5` (endurance record)).
- **Save list** (adventure, in place of the boxes, the tapes and the card choice): loading goes up to the boxes on the menu map
  (`McPrepBoxScreen`), and the update of `McLoadGameBoxes` becomes a modal with the `McBackground` frame and the `McTextBox` text (`McPage`
  fonts shrunk). On the right the `save.json` list (10 visible, up/down wrapping at the ends, left/right in steps of
  10); on the left the chosen save: the monster's logo, "on <level>", the level's wide photo with the 3D monster on top, "Score N", lives and
  "N of 11 levels" (the menu font has no `%`, `:` or `/`; the save's level is the next one to play). X loads through
  `MonsterMc::setSaveData`; triangle/circle goes back. Saving: the update of `McChooseSlot` (after the "save?") becomes the same modal;
  an empty slot saves directly, an occupied one asks for a second X. The first 100 ms do not read the pad (the X from the "save?" would arrive here). In the level the
  frame is shorter (the size comes from the `McBackground` animation, and `setDestDims` does not go past 1): the text heights are
  compressed, the frame goes straight to its final size (`timerGetFieldsLastFrame` does not advance there) and `McChooseSlot`'s `+0x274`
  (`stateIsOk`) is set as in the original. The controls legend only appears when loading (in the level the black bar would cover the fight).
  No memory card message appears in the game.
- **List images** (`native/wotm_savepics.hpp`): they come from the disc's `SHELL/SHELL.TEX` + `SHELL.RTX` (folder or ISO; after the fight the
  menu is not in memory): 256x128 logos at texIds 121..129 and 52 (Raptros); 512x256 photos in two T8 pieces of 256x256 (the square
  photo in the previous piece is not used). The palettes are 16x16 entries of the `.RTX` allocated in texture order (4 per T8, 1 per
  T4; the `.NGP` does not link these, the menu swaps them by switch). The rows go bottom to top. The modal posts the list every frame and the
  window draws between the frame (high-priority list) and the text, with a 0.2 s entry. With no logo (Spider, Ogre...) the name comes out as
  text. The 3D monster is the one from `wotm_model.hpp` ([MODELOS_3D.md](../../passos/MODELOS_3D.md)). A snapshot with fewer than 20 items counts as "no level" (black
  screen), except with a dialog in the high-priority list (the "save?" after the final Tsunopolis cutscene). The count adds what
  `collect` culled by the view (`Snapshot::culled`): the visible ones alone gave fewer than 20 with the camera turned to space in UFO or
  pressed against a wall, and the whole fight went black.
- **Save icon** (`native/wotm_saveicon.hpp`; `WOTM_SAVEICON_TEST=1` shows it every 3 s): the disc's `MEMCRD/ICON.ICO` (format
  in [FORMATS.md](../FORMATS.md)). Each write of `save.json` increments `g_wotmSaveCount`, and `wotmDrawScene` draws the spinning tape in the lower right
  corner for 1 s (0.15 s fade). Reads from the disc folder, from the ISO (`native/wotm_disc.hpp`) or from the copy the game wrote to the card. The
  `icon.sys` lights are not used.
- **Careful:** editing `save.json` with the game open can clobber a save (an editor open since before rewrites the old
  version). Edit with the game closed.

## Enemy bars (`WOTM_ENEMYBARS`)
- A block above each enemy's head, in place of the health icon (hook in `Hud::drawHealthIcon`/`ScreenPolys::addPoly`):
  portrait at full height on the left; on the right, health (`m_health`/`m_maxHealth`) on top and, below, the special button and the energy
  (`StaminaMeter`, +0x460; thinner and shorter). Each piece has its own black outline, the gray strip between them is shared and there is a
  black outline around the outside. Drawn through `ScreenRect::tex0` (`wotmBarTex`), respecting the split screen clipping. They come out under the player's HUD: `Scene::draw` draws them in 2D right before the `hud` list (`Scene::barPass`, one pass per view in split screen, each view in its own texture), and `drawScreenRects` skips them (`barsUnderHud`); without `barPass` (replay, corpus) they come out at the end of the frame, on top of everything.
- **Portrait:** last entry of the monster's `.RTX` (T8H 128x64; left half normal, right half rage). The hook finds the
  monster's file through the `epNode` of `m_cs` (+0xC) and the ranges of `fileStatus.ngpAddr`, and searches the NGP for that portrait's TEX0
  (`tbp0 == maxResAddr[i-1]`); cached per level load. Rage = `m_boostFull` (+0xF4), the same key as the `hierSetSwitch` in
  `Hud::update`. The texture is upside down in VRAM (the game draws with V = 0x80 - v): the rectangle goes from V 64 to 0.
- **Special lit** = `m_specialWeapon` (+0xF3) outside mode 9, like `isSpecialAvailable`, in the red of the player's HUD icon.

## 3 and 4 player split screen (`wotm_split4.inc`)
Always installed: acts when the game has 3 or 4 players (through the multiplayer menu or `WOTM_PLAYERS=3`/`4` with `WOTM_MATCH`). The engine
already has `viewInfo`, `worldCtx`, `viewDb`, look-at points and the particles' `viewPrevMat` with 5 views, 4 cameras, 4 HUDs,
`m_monsters[0..3]` for players and 4 `TokenManager`; `inputInit` opens 2 ports × 4 slots (controller = port + 2 × slot);
`SoundManager::m_events` is `[4][4]` by `m_index`. The cinemas' `viewToggleSplitScreen` does nothing with 3 or more views. The hooks:
- **Views:** on exit from `gameReestablishViews` (modes 3, 6, 7) views 0 to 3 become 320 × 112 quadrants (column `v & 1`, row
  `v >> 1`). With 3 players view 2 is the whole bottom row, 640 × 112, with a screen distance of 2/3 of the full screen's
  (`kStripFov`: the quadrants' would give ~118 degrees horizontally; the full screen's would cut the monster vertically); native drawing
  gives it a texture as wide as the window (`stripView` in `Scene`, for the bars above the enemies), and its HUD bar, attached
  to the camera for the quadrant projection, goes to depth × strip focus / quadrant focus and 160 × wide GS pixels to the
  left (`stripHudBar`): it sits where it would in the left quadrant. The 4 `ViewDef` live at the end of the upper RAM (retail only has
  8, none of them a quadrant), with half the full screen's screen distance (same FOV as the 640 × 224); `viewSetFov` rebuilds planes and
  matrices.
  `viewInfo[v].viewport` stays 1/2 (the cameras use the split screen POV table). `m_numCameras` = players.
  `viewGrappleConfig` returns view 0 to the half's `viewDef`: the hook reapplies the quadrant.
- **No unified view:** camera 2 (retail's unified one) is player 3's. Each frame's `SetOkToUnify` clears `m_camUnify`
  (`InitCCCamera*` returns without unifying). The victory pose unifies (full screen on camera 2); when the screen splits again, cameras
  2 and 3 go back to players 3 and 4. `ResetLevel` does not change camera 2's POV. Retail's `LeaveUnifiedView` only treats 2 monsters as
  split screen; with the quadrants it takes the 2 player path.
- **AI cameras:** retail's `SetAIMonster` puts every AI on camera 3 (`gameInitCamera(3, ia)`); here the AI only gets
  `m_cameraView` 3. `StateThrowBack::handlePreemption` (end of being thrown) puts the owner's `m_cameraView` camera on POV 0 without
  checking whether it is human; with an AI owner camera 3 does not change (`enterSubState` and `StateButtSlam` already check `m_playerNum`).
- **POV 3 of cameras 2 and 3:** POV 3 is the camera parked at `+0xD20` (`DetachCamera`, `TogglePOV`), which cameras 2/3 never have
  on retail. On entering POV 3 it parks where it is; camera 2 leaves the initial POV 3 (the unified one's rest state) for 0.
- **Loading:** from `LoadLevelFiles` to the entry of `InitPlayers` players 3 and 4 go through the AI path (`m_monsterSel[4..]`,
  `m_costume[2..]`, same disc file) and then go back to being players; `SetPlayerMonster` gets their costume instead of
  `m_costume[1]`. On retail, `LoadMonstersDB` builds the path of players 3/4 with player 2's monster. Players 3 and 4 take
  their controller configuration from `m_vibration[0..1]` (`Monster::playerInit` reads `m_ctlrCfg[m_index]`, which only has 2).
- **HUD:** retail's `Hud::initAfter` and `Hud::update` exit right away with index ≥ 2. HUD 2/3 is a copy of the HUD of the same column
  (`i & 1`) and runs the update like it, with `m_viewSlot`, the camera's `_cs` and the bar swapped for its own view's during the
  call (with the update paused midway by the scheduler, the swap holds until the resume reaches `ra`: `updateMessage` writes the
  "WINS" of the index 0 HUD left-aligned and the others' right-aligned); the two share the `_cs` and the bar animations, which each view redoes right before its `hier` ("Animações do HUD por
  vista" (per-view HUD animations): the copy's `_animHandle` point to the same instances). The rage bar is a layer (`AnimBlend` at +0x268) whose blend node
  lives inside the HUD: the copy's is marked active and never enters the `AnimPlayer` list (otherwise both views show the
  top layer); its time (`toTime`) goes to the column's node before evaluation and enters the state saved per HUD. With `m_numMonsters` ≠ 2 the bar stays at the full
  screen position, which is the quadrant's shape. The HUD text is placed as in a 224-line view starting from the top of the quadrant: in native, what
  falls in the bottom half (the "WINS") moves up 112 (only when more than one view sends text; the pause dialog stays as it is). The
  enemy bars turn on by themselves with 3 or 4 players.
- **End of round (mode 3):** `EvaluateMultiPlayerBattleStatusNoAI` only handles 1 or 0 alive and `...AI` respawns slots 0/1 as
  players and the rest as AI. With the quadrants both change: win target as in `...AI`, otherwise each dead one in `m_monsters`
  respawns through `playerInit` (players) or `aiInit` (AIs). Dialog 5 is **modal** (runs frames and yields to the scheduler): it is called
  as a tail call, with the `ra` of `Evaluate`'s caller (through `callGuest`, with `ra` 0, "play again" would return to pc 0 and kill the thread;
  the runtime warns `[resume] thread N terminou em pc 0` (thread N ended at pc 0)).
- **Cinema** (presentation before the fight): at the start of each frame, cinema on puts the screen in a single view (`viewNumViews` 1, view 0
  with `viewDef[0]`, 640 × 224) and cinema off goes back to the quadrants, like retail's 2 players. On the way back all views are
  rebuilt (`endCinema` calls the toggle, which with 1 view recreates views 0 and 1 as halves).
- **Start:** in `gameGetStartPoint` (modes 2 to 6) the first human spawn uses list 1 of `StartPoints` and the AI one list
  2, in rotation; respawns, list 3. List 1 only has the points of retail's 2 players; a player beyond them spawns as an AI
  (`m_playerNum` 2 during the call), on list 2. On "play again" everyone respawns through list 3 (4 points); whoever lands less than 120 from
  another goes to list 2 (two monsters at the same point put NaN in the position through the push).
- **Motion blur:** with no hook, `MotionBlurAA::init` gets the 3 or 4 views (check `borrao_4`). They fit: `drawOverlay(campo, ímpar, vista)` (field, odd, view)
  addresses `0x7319F0 + campo * 0x400 + ímpar * 0x800 + vista * 0x100` and the TU's bss has 0x1000 bytes (the next one, `common/animation`,
  starts at 0x7329F0), that is, `[2][2][4 views][0x100]`; with 4 views init writes up to base + 0xBD4.
- **Controllers:** the runtime's controller stub has the multitap slots (`tools/runtime_patch/wotm-runtime.patch`: controller =
  port + 2 × slot, 8 controllers); `scePadRead` of slot 1 reads the devices of controller port + 2 (`wotm_pad.inc`): third and fourth
  raylib controllers. No hook in the `scePad*`. The `PS2X_PAD` script accepts `@3` and `@4` (slot 1 of the ports).
- **Native:** `Snapshot::views[3]`; capture of views 2 and 3 on exit from `hier(v, 0)` (fallback: entry of `hier(v, 1)`); quadrant
  textures composited with the black bars in a cross; vertical FOV from the view's height (only in the `ViewDef` above 32 MB); text, bars
  above the enemies, flares (`lensFlarePacket[v & 1]`, one copy per view, occlusion by the depth of the previous redraw) and the particles'
  previous matrix for 4 views. Shadows are rasterized once per redraw, with the shadow LOD like `hierShadow`.

## Elimination and minigames with 3 and 4 (`wotm_modes4.inc`)
With 3 or 4 players screen 5 shows retail's list (free for all, elimination, minigames) and only the monster selections are ours
(the big-screen one; in the minigames the choice from screen 14 comes to screen 6 in place of the arcade, with camera animation 8 in reverse). Direct
match: `WOTM_MODE`. The rules, by hook:
- **Elimination (mode 6):** continues and wins per player; the Shell's two `m_continues` are 0 or 1 during
  `StateDeath::transitionInto` and `StateVictory::transitionOK` (ends only when one is left). Death with a continue: retail's dialog 8 for
  that player (`m_won[1]`), `SetPlayerMonster` and `playerInit`; the dialogs are modal and return through a trampoline
  (`EvaluateOnlineBattleStatus + 4`, which the game never executes) that does the rest and resumes `EvaluateGameStatus`, also when the thread
  yielded midway. With no continue and more than one in the fight: the player leaves (monster hidden, their camera follows whoever continues). One
  left: dialog 0xB; "play again" returns players 3 and 4 to their starting monster. Selection: costume 0, exclusive monster.
- **Dodgeball (7):** hits of players 3 and 4 outside `DodgeBallLevel` (retail's counter has 2 and the 3rd would write into the ball's
  count); "P3"/"P4" in views 2 and 3. The arena only has 2 start points: the extra player spawns at the point rotated 90° around their
  center (`wotm_split4.inc`).
- **Crush (9):** scoreboard of 4, winner by the highest of the 4 `TokenManager`, a tie at the top goes to sudden death with everyone; the camera frames
  the farthest pair.
- **Big Shot (8):** rotation in the 2 seats of `BigShotLevel` (3 turns per player); in the last one, the two best in the seats for
  retail's comparison (tie: the "king of the hill" between them) and the others standing at the waiting point.
- Minigame end dialogs with "Player 3/4 - scored".

## Level selection (`wotm_levelsel.inc`)
- **Lists:** the `screenLevelSelect` hook (screen 8) swaps the `g_levelList` of retail's four lists (`PO_1PFreeForAll`,
  `PO_MPFreeForAll`, `PO_1PEndurance`, `PO_MPElimination`) for a copy at the top of RAM (`PS2_RAM_SIZE - 0x300`): retail's levels
  in its order, then the missing ones from 1 to 16 (Training 12, Lake Powell 13, Tokyo Deathmatch 16 and, where they are absent, Mini Baytown
  14 and Volcano 15) and last RANDOM. Cursor, lock (`levelUnlocked`), sounds and confirmation are still the game's code. With
  `WOTM_HIGHRAM=0` elimination (the 10 monsters loaded at once) keeps only retail's levels and RANDOM. Log `[fases]`.
- **RANDOM:** it is level 17 (`dylan`, a team test level, with no files): the photo switch (`Shell+0x5D0`) has 24 children and
  `levelUnlocked` leaves it open. Its name in the `screenLevelSelect` table (`GameLevelLongNames_006EEEF8`) becomes "Random". In
  `changeScreen(8, 99)` it becomes a level drawn at random from the list, among the unlocked ones, without Training and Tokyo Deathmatch (team
  test levels) and without the fourth entry when the game skips it (mode 2 with 2 or more CPUs, mode 3 with a CPU), before loading. The announcer does not
  announce the randomly drawn level.
- **Photos:** `SHELL.TEX` has no photo of Training, Lake Powell and Tokyo Deathmatch; the switch children of those levels (and of 17) use
  another one's (Midtown Park, half of Rosdale Canyon, half of Tsunopolis). The photo object draws with its own texture
  (`Scene::nodeTexture`), in scene order, so the grain and the big-screen film pass over it as in the other levels. The photos:
  `levelpics/<nome>.png` (`training`, `lakepowell`, `tokyodeathmatch`, `random`; 2:1, photos taken in the port's photo mode), looked up
  in `mods/<mod>/levelpics/`, `levelpics/` next to the ELF and `levelpics/` at the repo root. With no PNG the game's photo stays; RANDOM with no PNG
  is a mosaic of the level photos from `SHELL.TEX` (`savepics::Drawer::levelTexture`), darkened, with a "?". The texture goes in like the
  game's: rows bottom to top, alpha 0xFF (that of the SHELL photo palettes, which drawing takes above 1) and repeat (the
  object's UV goes from -1 to 0). The object with a single texture (13, 16, 17) maps the same texture on both halves: U is redone from the position
  across the width (`Scene::patchMesh`, a copy of the mesh in the cache, because the resident arena keeps the vertices by pointer).
- **UNUSED badge:** on levels 12, 13 and 16 (not on RANDOM), a red badge with a border and white letters to the right of the level name, which
  `screenWriteInstructions` writes centered at y 10. Position, height and alpha come from the title glyphs in the frame (`Scene::text`, the ones at the
  top of the screen); drawn after the game's text (`drawBadge`).
