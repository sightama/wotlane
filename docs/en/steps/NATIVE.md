# Native layer (native/): drawing, textures, characters

(Split out of [NEXT_STEPS.md](../NEXT_STEPS.md); the index is there.) This file keeps **what is known**, not the diary of the investigations. The full account (discarded hypotheses, intermediate measurements) is in the earlier version: `git show 01050d2:docs/passos/NATIVO.md`.

## Overview, files and flow
The scene is read straight from EE RAM and drawn with raylib, without VU1/GS, using the game's camera. Files:
- `native/wotm_native.hpp` (single header: `Ram`, matrices, `decodeObject` = the `polyPkt` mesh, `Scene::collect/draw`, camera), `wotm_gs.hpp` (GS addressing, textures), `wotm_fx.hpp` (particles), `wotm_fmv.hpp` (movies), `wotm_snd.hpp` (sound), `viewer.cpp` (standalone viewer: free/game camera, `--shot`, `--texdump`, `--lod n`, `--cam`, `--disc`, `--rtx`), `fmvplay.cpp`, `build.bat` (MSVC; raylib from the runtime clone). Formats in [FORMATS.md](../FORMATS.md); offline mesh reader in `tools/ngp.py` (`TRACE` shows MSCAL/MSCNT per sub-packet).
- **Offline iteration (seconds):** the runtime writes `ram_<q>.bin` + `vram_<q>.bin` (`PS2X_DUMP_RAM="3300,3900"`) and `build\viewer.exe ram_<q>.bin` draws it. Dump of the open runtime: `python tools/pcsx2_auto/ramdump.py <discroot>/SCUS_971.97 saida.bin ps2EntryRunner` (the same script reads retail PCSX2).
- **Live:** `PS2X_SCENE=1` (with `PS2X_NO_VU1=1 PS2X_NO_VIF1=1 PS2X_NO_GS=1`) draws into a 4:3 render texture on top of the GS frame (`wotm_live.inc` -> `wotmDrawNative`); with no level loaded the GS frame continues. To run: `run_live.ps1` in the `wotm-recomp-win` clone (`-Auto 0` to play, `-Stats 1` logs `[native]`), or `WotM_Launcher.exe`. Keys: **F3** FPS counter (off at startup), **F11** toggles fullscreen and windowed, **F1** debug menu (cheats; "debug menu" section).
- **Rebuilding the runtime after touching `native/`:** `build_runtime.bat` at the root (or `tools/build_runtime.ps1`). Ninja **does not track** `native/*.hpp` or `native/runtime/*.inc` (they live outside the PS2Recomp tree): the script touches `ps2_runtime.cpp`; without that it prints "no work to do" and the game keeps the old drawing.
- **Addresses by name (since 2026-10-15):** `native/wotm_syms.h`, generated by `python tools/native_syms.py --gen` from `symbol_addrs.txt`, provides `wotm::sym::<data>` and `wotm::fn::<function>` for the ELF's 7,282 symbols (gcc 2.95 names with `$`/`.` replaced by `_`; those starting with `_` or clashing with an MSVC macro get an `x` prefix). In new code, use the name, not the number; `--audit` lists what is still raw in `native/` (28 literals remain that are fields inside a symbol, whose correct name is the one from the types header, and ~40 that have no symbol: bss `D_*`, masks, VRAM addresses) and `--apply` replaces the exact ones. Regenerate the header when `symbol_addrs.txt` changes.
- **Where the runtime code lives (since 2026-10-15):** the hooks and game-specific code that run inside the runtime are in **`native/runtime/`** in the repo: `wotm_live.inc` (live drawing, boot trace, watchdog, movies; includes `wotm_snd.inc`, `wotm_pad.inc` and `wotm_padsel.inc`: per-player controls and side selection), `wotm_scene.inc` (entry point included by `ps2_runtime.cpp`; includes `wotm_vu1check.inc`), `wotm_vu1check.inc` (VU1 vs native check, snapshot and `--vu1cmp`), `wotm_overrides.cpp` (game clock, `WOTM_MATCH`, `AIVSAI`...) and `wotm_vu0_native.cpp/.h` (dispatch of the VU0 microprograms; the translated `.gen.inc` goes to `<build>\wotm_gen`, outside the repo). The fork's CMake (`-DWOTM_NATIVE_DIR=<repo>/native`, mandatory) includes `native/` and `native/runtime/` and compiles both `.cpp` files. The patch `tools/runtime_patch/wotm-runtime.patch` holds only the PS2Recomp seams (CMake, `main.cpp`, taps in VIF1/VU1/memory, scheduler, pad, profiling). A change in `native/runtime/` is a normal commit in the repo; a change in a seam requires regenerating the patch.
- **Level change (`levelSignature`):** a hash of only the header of the level image at 0xA00000 (N + N pointers) and of `tempVramTexAddr`. Until 2026-10-14 it covered the whole first KB, which includes live nodes (the menu rewrites floats at +0x3E0..+0x3F8 during transitions): the scene was invalidated every frame, ~870 meshes and ~80 textures reloaded, drawing took 50-70 ms and the screen ran at ~16/s during menu transitions (with or without interpolation). Diagnosis: `WOTM_CAMLOG=1` (one `[cam]` per draw).
- **Without VU1 nobody completes the packet:** the game waits for `objsInPacket | objsInAlphaPacket` (0x6F87A0/A4) to reach zero in `rtWaitForVu1` (hooked) and in a loop embedded in `particleDraw` (0x21B8A0); with `PS2X_NO_VU1` the presentation (60 Hz) zeroes both. Old experiment variables: `PS2X_GS_UPLOADS`, `PS2X_VIF1_UPLOADS`, `PS2X_NO_VU1=2` (no longer needed).

## Textures and palettes
- **Pixels:** `texInfo[texId]` (0x50F100, 16 B per entry) points to a packet: width `+0x24`, height `+0x26`, TBW `+0x2A`, PSM `+0x2B`, **linear** pixels starting at `+0x80` (T8 = 1 byte, T4 = 2 per byte, low nibble first). The `TBP0` of the object's TEX0 is usually 0 (`texm` patches it at draw time) and is not used.
- **Palettes come from the disc's `.RTX`**, never from the dump's VRAM (which holds menu leftovers). Entries of `(word0 >> 2) * 16` bytes, 16 B header (GS descriptor at `+8`: relative DBP in the halfword `+0xA`, TW/TH in bits 40..47); 16x16 CT32 = 256 colors (1040 B), 8x2 = 16 colors (80 B). `Scene::loadResources(ram, raiz)` indexes by **absolute CBP** (`rtxPal`); it is idempotent.
- **Base of each `.RTX`:** the game stacks level, players and AIs in load order; `fileStatus` (0x445390) holds `names[i][9]` (+0xB1) and `maxTexAddr[i]` (u16, +0x14C). Level base = `tempVramTexAddr (0x6F8818) >> 6`; base of file `i` = `maxTexAddr[i-1]`. Lookup: `LVL/<nome>.RTX`, `MON/<nome>.RTX`, `<nome>/<nome>.RTX` (menu: `SHELL/SHELL.RTX`) and `SHELL/<nome>.RTX` (LOAD, UI, SHELL2, PRESHELL).
- **CSM1:** 256-color CLUTs have bits 3 and 4 of the index swapped; logical entry `i` = word `(i & 0xE7) | ((i & 8) << 1) | ((i & 0x10) >> 1)`. Only in T8/T8H (without it: grainy portraits and monsters, without the yellow spikes).- **PSMT8H/4HL/4HH** (menu: screens, fonts, logos, 512x512 portraits): `texInfo` does not point to the right pixels; the pixels are in the `.RTX` (0x80 B header, psm in bits 32..37 of the desc, sizes `0x1080`, `0x880`, `0x40080`). `TEX0.TBP0 == DBP` of the entry; 4HL and 4HH share the DBP (the two nibbles of the same byte). Stored in `rtxImg[(psm<<16)|DBP]`. The entry with size 0 is the last in the file and also counts (in the monsters, the HUD portrait); in the monsters the DBP is relative and adds `fileStatus.maxResAddr` (+0x168) of the previous file, as in `texmResRelocate`. Texture 180 (128x128, tbp0 4096) comes from a file not yet identified.
- **Alpha:** texture and vertex go in **raw** (no `fixAlpha`, no ×4): the GS blends with As = At·Av/16384, and the `Scene::draw` shader does `3.969·t.a·v.a` (up to 255/128; in the common blend, As above 1 comes out in two extra passes, `gsBlendOver1/2` in `wotm_fx.hpp`, since 2026-10-19) (CT24 and the CT16 bit give 0x80; untextured sections use `gsWhiteTexture`, alpha 0x80). Measurement and captures in [VU1CHECK.md](VU1CHECK.md), "Escala do alfa" (alpha scale). Object UVs = `int16/4096` normalized by size (checked against retail; buildings go up to ±8 and repeat on purpose; UV outside 0..1 requires `TEXTURE_WRAP_REPEAT`).

## Meshes and draw state
- **Point lights (2026-10-17):** fire (breath, `Weapons::CreateFire`, `Monster::lightOnFire`) creates lights in `pointLights` (0x6DFCE0: 32 `PointLight` of 0x40, position +0x10, range +0x1C, color +0x20, falloff +0x2C = range²/(16·intensity), enabled at +0x38). In pass 1 `hier` calls `GetClosestPts` (up to 8 enabled lights closest to the camera, for VU0 memory; with `closest[0] < 0` the count is 0 and the rest of `closest[]` keeps stale garbage). `hierTraverseAsm` calls VU0 program 0x748 for OBJECT with `pointLight` (0x80), `objType` 0 and, in a `_cs`, `ptLightMe` (+0xA9): with R = rows 0-2 of the matrix and T = row 3 minus the camera (camera-relative stack), v = Rᵀ(L − camera), it touches if |T + center − v|² < range² + radius², up to 3 lights, and sends T − v (q169-q171). With a light, `pktAddVu1ObjAsm` replaces the light program with 0x15D8 (before `dirLight`): color = min(255, color·q5 + Σ color_k·min(0.5, max(0, (L_k − p)·n)·falloff_k/|p − L_k|²)), n = normal/128, no directional light. `Scene::objectPointLights`/`pointRgb`; corpus snapshot `luz_pontual` (point light); check dump with the `ptl` line (q169-q175); `WOTM_PTLOG`.
- **Vertex alpha:** almost everything has ~0x42 and is opaque; VU1 sends it as is and the scale is the GS's (see "Alpha" above). The template's `PRIM.ABE` does not decide blending on its own; the shader does `discard` below ~6%.
- **ADC (STMASK + S-8):** skips only the triangle ending at that vertex; the strip continues. Treating it as a restart loses triangles (holes, torn sky). `tools/ngp.py` still uses the old model.
- **Multitexture:** up to 5 textures per object (`texId[5]` at `+0x50`, `numTextures` `+0x5A`, `gsTexCtx[i]` at `+0x70 + 0x30*i`). The 4th word (high REGS) of each section's GIF tag is the **selector `1 + 3*slot`**, with two rules: `sel = 0` **inherits** the previous section's texture (the GS keeps TEX0; state in `MeshData.curSlot`, initially 0), and **bit 15** is a flag (slot = `(sel & 0x7FFF)`). Without this: terrace with wall texture, "camouflaged" police cars (checked against retail). Open, low risk: 1st section with `sel = 0` (only texId 189).
- **Blending:** the GS state of a translucent object comes from the **`ctx` of the nearest parent node that has one**: GROUP, TRANSLATE, ROTATE and SCALE at `+4`, ANIM_XFORM and ANIM_SCALE at `+8` (`Scene::CtxScope`, since 2026-10-17); with none, `ctxGetDefaultGSCtx` (0x44). It is an A+D tag with `ALPHA_1` at `+0x20`, `TEST_1` and `ZBUF_1`. `0x44` = normal, `0x48` = additive (Kineticlops), `0x42` = `Cd - Cs*As`, `0x46` = `Cd*(1-As)` and `0x81` = `(Cd-Cs)*As` (Kineticlops in color 3). `Scene::groupState` reads the `ALPHA_1` byte (`DrawItem::blend`; `gsBlend` in `wotm_fx.hpp` translates any `(A-B)*C+D` into GL factors) and the `TEST_1` threshold (`DrawItem::aref`, shader uniform `alphaRef`; default `kGsAlphaRef` = alpha > 8, the common `0x8D`; ATE 0 or ATST ALWAYS = no test, `kGsAlphaNoTest`, since 2026-10-17). The frame goes to the window **without blending**: the framebuffer alpha is the blends' alpha, not opacity. **Order (2026-10-17):** outside the alpha OT (bit `0x8000` of the flags), opaque and translucent objects come out in traversal order, writing Z according to the `ZMSK` of the inherited `ZBUF_1` (`DrawItem::zmsk`); the alpha OT comes after, by depth band and LIFO (`alphaBin`, `inAlphaOT`), and shadows last ([VU1CHECK.md](VU1CHECK.md), "Ordem do hier e OT de alfa" (hier order and alpha OT)). `hierTraverseAsm` writes the current ctx into every object of the alpha OT, so the state does not leak from one object to the next (the explosion sphere came out with 0x44 because its ctx comes from a TRANSLATE/ANIM, not from a GROUP).
- **zBufferFudge** (`HierObject +0x28`, 1.0..1.12): **>1 = closer** (in the GS larger z is closer and z ~ 1/distance); native scales the vertex along the eye ray by `1/fz`. With the wrong direction, labels in the options menu, lit windows and dirt trails disappear.
- **Sky:** `worldCtx[0]` `+4/+8/+0xC` (`skyCs`, `skyCs2`, clouds), before the world, without depth, at `skyCs->trans` like `hierTraceSky` (not at the eye). `trans` only changes through `viewSetSkyTrans`, which `hierSetCamera` calls after the traversal passes a camera node: in the menus that is every frame (trans = eye); in a fight the sky stays where the last locator camera left it and the game camera moves around it (parallax of the mountain ring, `tex 108`; since 2026-10-18, before that it was drawn at the eye). It is included in the check's triangle comparison. **HUD:** ids 0x1C20..0x2133 (except button icons, below) are `hier` objects that the game places in front of the camera every frame (`Hud::update`, `Letterboxing::update`); they go to `Scene::hud`, drawn last, without depth (details in [VU1CHECK.md](VU1CHECK.md), "Corrigido" (fixed)). The HUD that comes out as a GS packet through `ScreenPolys` (the health marker of the other monsters) is read at the entry of `ScreenPolys::dmaData` (`wotm::readScreenPolys`) and drawn like the text, before it ([VU1CHECK.md](VU1CHECK.md), "Corrigido"); `Hud::dmaPacket` only exists with split screen, which native does not have.

## Hierarchy, LOD and characters
- **Rigid:** `CHAR_INSTANCE` (`+4` = `animOutput.val`, `+0xC` = `atMat`, `+0x14` = `animMatrixPtr`, `+0x18` = `animPktPtr`, children at `+0x2C`). `ANIM_XFORM` (op 17): the game computes the local matrix in `atMat[matrixIdx]` (`+0xC4`; `visible` float `+0xC`, children `+0xCC`); native only reads it.
- **Op 35:** container of `ANIM_XFORM` (count `+4`, children `+0xC`) with the monsters' **rigid parts** (hands, claws, head, thruster). Ignoring it removed Robo-47's hands and head and Togera's blades.
- **`ANIM_SCALE` (op 38):** visibility is `val[vidx]` (`vidx` int16 at `+0x10`): 0 skips the node and its children, `-1` = always. `+0xC` is static (reading it left Robo-47's blades and flame always visible).
- **`DESTRUCTIBLE` (op 39):** descends only into `child[whichChild].child`, with `whichChild` = `INTERACTIVE_STATE +4` of the parent. Validated in a match with attacks (building in ruins). Still missing: dust/fire/`Debris` and the `actions` of the state change. `WOTM_DESTRSTAT=1` counts per state.
- **`CONTROL` (op 8, "ghost" building):** `+4` solid, `+8` ghost version (or null = disappears), `+0xC numVolumes`, `+0xE volType`, sphere `+0x10/+0x1C`, BSP volumes at `+0x20` (leaf `0x200` = air). `volType == 0`: eye outside the air -> child2. `volType != 0`: segment eye -> sight point (`g_cameraLosPoints` 0x50F020, direction in xyz and distance in w; count at 0x50F0C0) crossing a solid leaf -> child2. `Scene::ctrlChild` reimplements it (the original `bspVecTestIn` is asm); only view 0 and up to 2 points.
- **LOD:** picks the highest index whose `switchOutDis` (`+0x20 + 16*i + 4`, squared distance) is larger than the squared distance from the center (`+0x10`, transformed) to the eye; none -> not drawn. Index 0 is the coarsest. The `fade` between LODs is not reproduced.
- **Skinned (monsters):** `CS` 96/97/101/105/106/107 -> GROUP -> `CHAR_INSTANCE` -> `SKEL_BONE` + `LOD`. The `polyPkt` is a **chain of sub-packets**: tag `0x600100b4` (bit 16 = skinned; the low 16 bits are not a size), `UNPACK V4-32 @0xB5` (up to 190 vertices: xyz + weight in w, **bone code in the low 8 bits of x, y and z**), normals `V3-8 @0x175`, strip sections; each sub-packet ends in two NOPs and the next one comes qword-aligned after zeros.
- **Matrix palette:** `animPktPtr[OBJECT+0x68]` (index of the OBJECT itself, as in `pktAddVu1ObjAsm`; negative = no palette, the game sends the packet at `+4`. It is not the LOD index: the Dragon has body and wings in the same LOD, at 5 and 6) -> 1st tag `3000007d <address>` -> block of 125 qwords (the Dragon's body uses its own palette of `0x41` qwords, 16 matrices, for the same VU1 address); bone code = qword address in VU1: `slot = (código & 0x7F) / 4`, matrix at `bloco + 0x10 + 0x40*slot`. `animMatrixPtr[i]` points to **shuffled** slots (do not use `animMatrixPtr[código/4]`). Bit 0x80 is not used by the microcode.
- **Weights (VU1 microcode disassembled with `tools/vu1dis.py`, output in `build/vu1/`, game code):** 3 bones per vertex, `w1 = w`, `w2 = frac(w * 2048)`, `w3 = 1 - w1 - w2`; position = `w1*Mx*p + w2*My*p + w3*Mz*p`. Implemented in `skinVertex`.
- **Robo-47:** the dome's **electric arc** is the `fx[]` of visual type 7 (VisArc), `texLoad[0]` 57; drawn by `Particles::arcQuads` (97.5% matched with VU1; [VU1CHECK.md](VU1CHECK.md), "Arco elétrico" (electric arc)).

## Physics with `dt = 1/updateRate` (runtime)
The game integrates several things with Euler using `dt = 1 / timerGetUpdateRate()` (0x2236D8). On retail the rate is 60 or 30; in the runtime it oscillated between 60 and 8 (vsyncs arrive in jerks: one game frame lasts 1 vsync, the next one 6), and with a large `dt` the integrators diverge:
- **Congar's fur "exploding":** the 8 fur bones (4, 8, 11, 13, 20, 22, 26, 28) are **springs** (`BoneSpring::update`, 0x11B5C0: `Spring::applyForces` + `PointMass::resolveForcesEuler`). The deviation of ~5 to 6 between `atMat.linha3` and `nó.t` on those bones is **normal** (the same on retail). The spring is only stable with `dt²·k/m` below ~4. Ruled out by measurement: the VU0 interpreter (15 million `vcallms` compared with the reference, `PS2X_VU0_VERIFY=1`), `vf0`, the native layer.
- **Monster spinning on its own (camera along with it):** `MonsterDynamics::updatePosition` (0x165100) integrates `ang.z` with damping ≈ `-40.5·velRot`, stable only with rate ≥ 21; at rate 10 the velocity reverses and grows. `WOTM_TURNLOG` prints `[turn]`.
- **Fix (2026-10-14):** `timerGetUpdateRate` returns at least `WOTM_RATEMIN` (default 30; 0 disables) for the whole game (`wotm_overrides.cpp` in the runtime). On slow frames the game runs a little slower instead of skipping.
- **Underlying cause (fixed on 2026-10-14):** the game measures logic duration with timer 1 (`fields = ticks / 9619`, `updateRate = 60 / fields`), and the timer advances with the EE's virtual clock. The `particleDraw` loop at 0x21B8A0 waits for `objsInPacket | objsInAlphaPacket` to reach zero (VU1 completion); without VU1 the presentation was what zeroed them, and the loop burned 32 virtual cycles per iteration, so the game measured 2 to 4 fields at random. Fix in `main.cpp` (with `PS2X_NO_VU1`) and `EeScheduler::checkpointDue`: zero the counters at the entry of `particleDraw`, do not count cycles in that loop, and make the virtual clock follow the wall clock while the logic runs. Measured (`WOTM_FIELDLOG`, 1 vs 1 fight in Canyon): 96% of frames at rate 30, game time ≈ real time.
- **The logic is not 30 by design:** the game uses 60 whenever the logic fits in 1 field (`timerWaitForMinUpdateRate` only waits longer if the rate exceeds `D_006F8DD8`). The 30 was runtime slowness.
- **Fields = vblanks of the frame (2026-10-14, `wotm_overrides.cpp`):** the frame starts a few host ms after the vblank, so the logic crossed a vblank with timer 1 below 1 field and the game counted 1 field in a 2-vsync frame (18% of frames, game ~15% slower than the clock). At the entry of `timerWaitForMinUpdateRate` the field counter becomes at least the number of vblanks since the start of the frame (marked by the `timerGetCurTics` called at its end or in `timerSetFrameStart`). Central: game time went from 80% to 97% of real time. The `particleDraw` wait also zeroes the counters inside the loop itself (they rise inside it).
- **Timer from the host clock (2026-10-18, `wotm_overrides.cpp`; `WOTM_TIMER_EMU=1` goes back to the emulated timer 1):** `timerGetCurTics` was replaced entirely and returns the host clock at timer 1's frequency (576 kHz, BUSCLK/256, mode 0x82 of `timerInit`; 9619 ticks per field). `timer1Handler` keeps running, because it waits for vsync, but the fields it adds (`ceil(T1 / 9619)`, up to 16) come from host time since T1 was last zeroed (end of `timerWaitForMinUpdateRate`, `timerSetFrameStart` or the previous `timer1Handler`). The computation is done **at entry** and the emulated T1 is zeroed so the original adds 0: `timer1Handler` almost always blocks in `sceGsSyncV`, and resumption jumps straight into the middle of the recompiled function without going through the wrapper; an "after" in the wrapper does not run (this applies to any hook on a function that blocks). The rest of the timer (`timerSetFrameStart`, `timerEndOfRealTimeProcessing`, `timerGetFrameTime`, `timerGetAverageFrameTime`) only sees T1 through `timerGetCurTics`. The "fields = vblanks" fix remains: the delay between the vblank and the start of the frame (`wotmCaptureFrame` runs there) also exists with the host clock. Measured (AI vs AI fight in Centro, `WOTM_FIELDLOG`, 55 to 75 s): without load, 100.1% of real time and 60 f/s on both clocks; with an artificial 0 to 25 ms delay in the middle of the logic (frames of 1 and 2 fields), 100.2%; without the vblank fix, ~95% to 97.5%. Menu through the pad script up to the fight: the same. The scheduler patches (virtual clock following the wall clock in `checkpointDue` and the delay added in `waitForEvent`) stayed until vsync was driven by the host: switched off in a test, the host timer still measured correctly, but vsync stopped pacing the frames (frames of 19 to 31 ms instead of 2 vsyncs, because the vblank deadline also required the virtual cycles to reach it), and the game ran at 138%.
- **Vsync from the host clock (2026-10-19, `EeScheduler.cpp` in the patch):** every scheduler deadline (vblank, alarm) expires only by the wall clock, and the two patches were removed. Virtual cycles remain for the EE timers and the time slice between threads; idle time adds the time actually spent stopped. Measurement and what remained open in [BOUNDARY.md](BOUNDARY.md), step 4. Test with slow frames: `WOTM_LOGICDELAY`.
- **VU0 (2026-10-14):** the interpreter (`VU1Interpreter` with a pipeline model) dropped from ~9.7 to ~3.9 µs per `vcallms` without changing results: no longer zeroing the 64 KB XGKICK buffer on every call, committing only the queues with something ready, `normalizeOperand`/`broadcast` inline, decoded pair by reference. Verified on an offline bench that re-runs the `PS2X_DUMP_VU0` samples and compares against the upstream interpreter (336 thousand executions with perturbed inputs: 0 differences).
- **Native VU0 (2026-10-14):** `tools/vu0native.py` reads the VU0 microcode from the ELF (VIF packet with MPG at file offset 0x15C890) and generates C++ for the 14 microprograms the game calls. The generated `.inc` is a translation of game code and stays outside the repo: `build_runtime.ps1` generates it in `ps2xRuntime/src/lib/vu/` when it is missing or when the script changes. `wotm_vu0_native.cpp` dispatches by pc and only uses the native version if the FNV-1a hash of the program's slice of code memory matches; the hash is recomputed when the code generation changes. `WOTM_VU0_INTERP=1` sends everything back to the interpreter, and `PS2X_VU0_VERIFY` and `PS2X_DUMP_VU0` also force it.
  - **Arithmetic:** the same as the interpreter, on all 4 lanes at once (SSE for float, AVX for double): normalized operands, float computation rounded toward zero and the result classified by its double value (zero, overflow, underflow), with the product's sticky bit in madd/msub.
  - **Branches and flags:** the generator compiles blocks specialized by the pipeline state at entry (cycles left until each VF/VI/ACC is ready, pending flags and where they are, VI saved for the next branch, `bal` return address). Stalls and the cycle at which each MAC/status flag becomes visible to `fmand`/`fsand` come from the state, without depending on the data. Branches become `goto`, and the 0x748 loop closes when the state repeats. 0x430 and 0x4D0 call subroutine 0x598 (sine and cosine with flag-based branches) and become 13 blocks each.
  - **Cross-check:** the cycle model matches the interpreter on the 11 straight-line programs. The interpreter's 4096-cycle budget, which cuts the program off in the middle, is not reproduced: native always runs to the end, like the hardware.
  - **Floating point:** the runtime compiles with `/fp:fast /arch:AVX2`, and with that the compiler fuses `acc + a*b` into an FMA, with a single rounding, while the VU rounds twice. The interpreter in the runtime therefore does not reproduce the VU bit for bit at that point. The native file compiles with `/fp:precise`, outside the unity batch.
  - **Bench:** in `vu0bench`, with native compiled as in the runtime, it is identical to the interpreter under `/fp:precise` across 840 thousand executions with perturbed inputs (extreme values, denormals, inf/nan, cancelling sums, random flags and VI), except those that exceed the budget. Against the samples recorded by the runtime there is a difference of 1 to 3 ulps, the same one the interpreter under `/fp:precise` has with them.
  - **Gain:** 13× to 28× per call (0x0: 3.5 → 0.15 µs; 0x1A8: 8.5 → 0.53 µs; 0x4D0: 11 → 0.58 µs).
  - **Automatic fight in Centro (1 vs 1):** CPU per frame dropped from median 15.0 / p90 18.6 / p99 23.4 ms to 4.7 / 6.3 / 10.0 ms. The logic stays at 60 in 99.9% of frames (before, 82%).

- **PS2Recomp bug fixed along the way:** a recursive function paused at its call to itself was treated as finished and the game jumped to garbage (`dispatchGuestBranch`, `ps2_runtime.cpp`). If it happens again, the `[resume]` log lists the last 64 resumptions before the invalid pc.
- **Build:** the unity build does not recompile the batch that includes `main.cpp` when only that file changes; `tools/build_runtime.ps1` deletes that `.obj` on its own.

## Runtime: host hooks end with `pc = $ra`
Every hook of ours (sound, movies, `rtWaitForVu1`, `hierFlushObjQ`...) is registered with `hostLeaf<f>` (`ps2_runtime.h`): if the hook did not change `pc`, it does `pc = $ra`. Reason: when the time slice ends right at a call, the scheduler resumes by calling `lookupFunction(pc)`; recompiled functions and stubs end with `pc = $ra`, but a raw hook left `pc` at its own entry and was called forever (the logic froze while drawing stayed live; seen with `pc = snd_FlushSoundCommands`). A new hook without `hostLeaf` brings the freeze back. Open: `callGuest` (`wotm_snd.inc`) calls game code inside a hook and can be interrupted the same way.

## Runtime: freeze and pace watchdog
On by default, in the presentation loop (`ps2_runtime.cpp`, next to `PS2X_DUMP_RAM`). `g_frame` (0x6F7E38) increments on every frame of the fight (`rtMain`) and of the menu (`ShellRtLoop::endField`, which also covers the pause dialog). If it stays still for `WOTM_WATCHDOG` seconds (default 8; 0 disables) while the screen keeps drawing, the logic has frozen. A movie (`movieIsPlaying`, 0x6F8650) does not count. This happens once per stop: `[vigia] CONGELOU` (watchdog: FROZE) lines with the EE threads (pc/ra to look up in `symbol_addrs.txt`) and the semaphores in `live.err.log`, plus `ram_vigia_<g_frame>.bin` and `vram_vigia_<g_frame>.bin` in the disc folder (`discroot`), which is the cwd. When the game moves again, `[vigia] g_frame voltou a andar` (g_frame is moving again) is printed. The legitimate stops measured (menu and level loads: `zipBuildHuffmanTable`, `Shell::FadeScreen`) last 1.3 to 2.5 s. Pace: 2 s windows with the game running below `WOTM_MINFPS` frames/s (default 25) produce `[vigia] LENTO` (SLOW) and then `ritmo normal de novo` (normal pace again) with the duration and the minimum, without a dump. Windows with a gap of more than 1 s between frames are loading and are left out.

## Runtime: VU1 vs native check (`WOTM_VU1CHECK`)
Compares, per object and in numbers, what the VU1 microcode would send to the GS with what the native layer draws. It does not produce an image. Code in `wotm_vu1check.inc` (runtime); hooks in `ps2_memory.cpp` (origin of each chunk of the DMA chain), `ps2_vif1_interpreter.cpp` (origins up to each MSCAL/MSCNT), `ps2_vu1_core.cpp` (XGKICK output) and `main.cpp` (`hierFlushObjQ`).
- **How it works:** it runs in the usual native mode. VIF1 processes every chain that arrives (VU1 microcode and data kept up to date; without this only ~78% matched), but does not execute VU1 or feed the GS. Every `WOTM_VU1CHECK` seconds, on a fight frame (`g_frame` ≥ 30), `hierFlushObjQ` triggers the real DMA from the entry of `hier(0, 0)` to that of the next frame. Each XGKICK is broken down into triangles (strip orientation made equal to native's) and assigned to the native object whose `polyPkt` contains any of the origins of the chain chunks since the previous MSCAL. At the start of each chain, the native layer collects the scene with the RAM at that instant and projects with view 0's `worldToScreenMat` (`d = p - olho`, `X = l0·d`, `Y = l1·d`, `W = l3·d`, GS pixels centered at 2048). Each VU1 triangle matches the closest native one of the same object (vertices within 1 px). Only whole on-screen (640x224) and non-degenerate triangles are included.
- **Why collect per chain:** the chain references matrices and palettes in place (REF). Only the first packet goes out inside `hier`. At the end of pass 0, `hierCheckVifComplete` (0x2045A8, `bc0t`) says "busy" and the last packet, with the monsters, goes out through the DMA interrupt (`hierDmaHandler` → `hierFlushObjQ`), which the runtime delivers in the middle of the logic (`TheGame::Update`, `animationRunGlobal`). Collecting only at the entry of `hier`, monsters matched at 20% to 99%, depending on the frame. Answering "free" in `hierCheckVifComplete` sent the packet twice. The camera is copied into the packet, and a pass 0 chain can go out already inside pass 1. That is why native is projected with the camera at the entry of each pass and the one that matches best counts.
- **Back faces:** the microcode discards back faces in sections with bit 15 of the selector set (native does too, `Vtx::cull`; rule and exceptions in lead 11 of [VU1CHECK.md](VU1CHECK.md)). Those that VU1 draws through the clipping path match against the ones discarded by native and count as `costas pelo recorte` (back faces via clipping). When VU1 drew no back faces on an object, the leftover native ones count as `costas` (back faces), not as a difference.
- **Texture:** each matched pair compares the TEX0 in effect in the GS when VU1 drew (PACKED TEX0_1/TEX0_2 or A+D, between packets; context from `PRIM.CTXT`; `PRIM.TME` 0 = no texture) with the one of the section's slot in native (`texKey`/`objectTex0`). Only the fields that choose texels count (TBP0, TBW, PSM, TW, TH, CBP, CPSM, CSM, CSA).
- **Particles:** each system's packet lives inside its own `fx[i]` (`pkt` at +0), so the origin of the chain chunk tells the system. VU1 sends each particle as two triangles (pedestrians, stripes, type 7) or as a GS SPRITE (sprite, texSprite, debris, dust). The triangles become quads in pairs; native builds the same quads (`Particles::forEachQuad`, `Scene::spriteCorners` for debris), projected with the camera at the chain's instant or with one of the passes' (the one that matches best counts). Each quad matches if all corners are within 1 px. Output: the line `[vu1check] g=… particulas: sistemas, quadrados vu/nativo, casados %, SPRITE do GS (fora de `fx[]`), vértices não comparados (só pontos)` (particles: systems, vu/native quads, matched %, GS SPRITEs (outside `fx[]`), vertices not compared (points only)), the line `particulas por tipo (casados/vu/nativo)` (particles per type (matched/vu/native)) and up to 8 systems with the most difference (`fx`, preset, type, `n`, `sem pacote` (no packet)).
- **Particle color (2026-10-18):** in matched quads, each VU1 corner (the vertex's RGBAQ; for SPRITE, that of the 2nd vertex) against the closest native corner, with the color the drawing uses (`Particles::forEachQuadColored`, which shares `quadColor` with `drawSystem`; debris: `Sprite::gsCol`). Line `particulas cor: casados com cor | cor difere (RGB > 4) | alfa difere (> 4) | por tipo (cor/alfa/casados)` (particle color: matched with color | color differs | alpha differs | per type (color/alpha/matched)) and up to 6 systems with the 1st difference (VU1 and native RGBA).
- **Lines (2026-10-18):** XGKICK PRIM 1/2 (only `FX_LINE` uses them) against native (`pos` → `pos − vel`, the particle's color and alpha 0 at the tail). Matches both ends within 1 px; `so a ponta casa` (only the tip matches) = the particle's end matches and the other does not. Line `linhas: XGKICK N segmentos (fora de fx[]) | vu, nativo, casados | cor/alfa difere` (lines: XGKICK N segments (outside fx[]) | vu, native, matched | color/alpha differs); dump `line,vu|nat`, `linecam`, `linemat`, `linep`.
- **Fans (2026-10-18):** PRIM 5 becomes triangles (1st, second-to-last, last vertex) and enters the comparison like the rest. In the corpus they all come from the microprogram's clipping and cross the screen edge (they count under `fora da tela` (off screen)).
- **Texels (2026-10-18, only in `--vu1cmp` with images):** each XGKICK TEX0 is read from GS VRAM at draw time, the way the GS samples it (`decodeVram`: CT32/24/16, T8, T4, T8H/T4HL/T4HH; CSM1 palette through GS addressing), and compared, in matched triangles with the same texture, with what native decodes (`Scene::decodeTex`, raw alpha). RGB always, alpha only with TCC = 1. Line `texels: pares textura x objeto | iguais (<= 1), perto (<= 8), diferem, tamanho difere, VRAM com outra textura do mesmo TBP | uploads no quadro` (texels: texture x object pairs | equal, close, differ, size differs, VRAM with another texture at the same TBP | uploads in the frame) and up to 6 worst (`texels tex <id>`). In a fight no texture is uploaded within the frame: they are already in the snapshot's VRAM.
- **Output:** per check, one line `[vu1check] g=… objetos vu/nativo/ambos | tris vu (repetidos: o mesmo triângulo redesenhado, como a sombra projetada) /nativo, casados % (sem os repetidos), faltam (do VU1, sem par nativo), sobram (do nativo, sem par) (costas) | textura difere, sem TEX0 | XGKICK (todos os triângulos do VU1), fora da tela | sem objeto, cadeias, tempo da coleta, …, VIF1 fora de passo` (objects vu/native/both | vu tris (repeated: the same triangle redrawn, like the projected shadow) /native, matched % (excluding repeats), missing (from VU1, with no native pair), extra (from native, with no pair) (back faces) | texture differs, no TEX0 | XGKICK (all VU1 triangles), off screen | no object, chains, collection time, ..., VIF1 out of step) (invalid VIF1 codes since boot; nonzero = VIF1 read data as commands, see [VU1CHECK.md](VU1CHECK.md)). Then come up to 8 objects with the most geometry difference (`pkt`, `no`, `tex`, skinned, items), up to 8 with a different texture (`textura pkt`, with the most common TEX0 pair) and the origins of VU1 triangles with no native object. Collection costs 20 to 100 ms on one frame every N s. With `WOTM_VU1CHECK_DUMP=<prefixo>`, each check writes all triangles to `<prefixo>_<g_frame>.csv` for analysis (last column: TEX0).
- **Status and open leads:** in [VU1CHECK.md](VU1CHECK.md) (single source; do not duplicate here). References to "Corrigido" (fixed) entries (here and in the code) are in the history: `git show 5eca44b:docs/passos/VU1CHECK.md`.
- **Snapshot and check without the game (2026-10-15):** `WOTM_VU1CHECK_SNAP=<prefixo>` writes the session's sampled frames into a single file, `<prefixo>_<g_frame do primeiro>.vu1snap` (g_frame of the first one): in the first, the VU1/VIF1 state and the whole RAM and VRAM at the entry of `hier(0,0)` (~36 MB); in the following ones, the state and only the 4 KB pages that changed (~7 MB per frame in a fight). Within each frame, in the order they happened, each DMA chain (pages that changed, chunk origins and the bytes) and the entry of `hier(0,1)`. What VU1 sends to the GS is a function of only that (VIF1 reads the copy of the chain, never RAM). `WOTM_VU1CHECK_SNAP_MAX=<MB>` (default 2048) stops writing at the ceiling. **Trigger, burst and shot limit:** `WOTM_VU1CHECK_WHEN=fx:<tipo>|preset:<fxId>|frame:<a>-<b>[,...]` only samples when the condition **becomes true** (edge: the event was born; a permanent emitter, such as the volcano smoke, fires once, an explosion fires on each new explosion). `fx:` is the visual type, `preset:` is the system's `fxId` (names in `tools/fx.py`) and separates the volcano smoke from a building's; the `WOTM_VU1CHECK` period becomes the minimum rest between shots. `WOTM_VU1CHECK_BURST=<k>` samples `k` consecutive frames per shot and `WOTM_VU1CHECK_SHOTS=<n>` limits the session's shots. To see a rare event, you do not wait for the clock: you provoke the event (`WOTM_MATCH`, `PS2X_PAD`) and record the burst when it appears. With the snapshot on, the runtime turns on `PS2X_GS_UPLOADS=1` by itself: texture and CLUT uploads now reach the GS (without rasterizing), so the file's VRAM has the textures the reference image needs. Since 2026-10-18 it also intercepts `texmActivateTexture` (a miss in the level's texture cache): outside the sampled frame the `hier` chain does not go to DMA, and the swapped texture's upload rode in it; the hook sends the upload packet straight to the GS (the mipmaps of `texmSetMipMapTbl` are left out). Older snapshots have the old texture in those slots. `tools\vu1cmp.ps1 <arquivo ou pasta> [-Frame <g_frame>] [-Dump <prefixo>] [-Full] [-NoPng]` (file or folder) runs `ps2EntryRunner --vu1cmp <arquivo>...` (since 2026-10-18 one execution for all files: opening the runtime, with window and audio, cost more than the comparison; GS, VU1, the native presentation and the lens flares restart from scratch for each file, and the output and images are identical to those of one process per file, checked on the corpus's 24): it opens the runtime without the game, restores the state, reapplies the chains with the same native collection and prints the same `[vu1check]` output for each frame (checked: 447 of 447 lines identical to those of the live check in a 21-frame session, apart from collection time; 5 s for the whole session). A frame cut off by the process dying is ignored with a warning; the previous ones count. The replay runs on a thread with a 512 MB stack: the main thread overflows. **Images** (default; `-NoPng` disables), next to the file, `<arquivo>_<g_frame>_{ref,nat,diff,trio}.png` at 640x448: `ref` is the runtime's software GS fed with the same packets (XGKICK, PATH2 and the frame's GIF channel), **an approximation of the PS2 GS, not the GS**: it guides the eye, the criterion is still the table; `nat` is the native layer through the same function as the live game, with the RAM at the frame's entry and without the FPS counter; `diff` marks in red the pixels that differ by more than 24 in a channel, over the darkened reference; `trio` is the three side by side. Expected differences: the `ScreenPolys` health marker, which the runtime's GS does not paint (PCSX2 does), the sky (GS gradient/dither) and the passes' camera. For the runtime's GS to draw the frame, the replay does a warm-up (runs the frame once through the GS only, restores VRAM and VU1 to the entry state, reapplies the GIF channel packets, which clear Z, and forces FRAME to this frame's buffer, because the frame's drawing environment was sent in the previous window). It serves as a regression corpus: a folder of sessions named after what they show, run in full after each change in `native/`. Delete the sessions once the fix is validated (rule in [CLAUDE.md](../CLAUDE.md)).
- **Out of scope:** vertex color, blending and alpha (the opaque explosion); VU1 lines (`line`) and fans are only counted.
- **Full emulated path (without `PS2X_NO_VU1`):** the fight stopped on the first frame (the `particleDraw` loop) and, with that loop released, crashed in `GS::consumeLocalToHostBytes` (VRAM read from `sceGsExecStoreImage`, called every frame from 0x2153FC). The check does not use that path. To locate a `[CRASH] exe+0x…`: relink with `/MAP` (`set _LINK_=/MAP:<arquivo>`, delete the exe and run `build_dev.bat`) and look for the largest symbol ≤ the address.

## Lessons on method
- **An object half disappears and the wireframe is whole: suspect render state before geometry.** The enemy monster's "holes" were culling turned back on before the flush of the last batch (the GL state applies at flush time): flush (`rlEnd(); rlDrawRenderBatchActive();`) before changing state. A long hunt through palette, weights and pose found nothing because mesh, palette and matrix were correct.
- raylib: `rlBegin` with a different mode resets the texture (call it before `rlSetTexture`), and flush the batch on every texture change.
- `WOTM_NOSKIN` is not a reference pose (positions are local to the bone); `WOTM_ONLYTEX` on its own removes body parts and creates false holed silhouettes.
- `getenv` inside the `drawList` vertex loop brings the menu down to ~1.6 FPS.
- A retail dump from PCSX2 brings the geometry, but the texture pixels have already been reused; since `texInfo` is identical between retail and runtime, copying the pixel packets from the runtime dump gives a textured **hybrid dump** in the retail pose.

## Movies (FMV)
- **Cut:** the game's decoder (SCE's "ezmpeg" sample, IPU via DMA) depends on the IPU, which the runtime does not emulate. `native/wotm_fmv.hpp` replaces `playMpegMovieWithDB` (0x20F4B0) and `updateMpegMovieDecoding` (0x20F540) for the fullscreen ones (at the end: `movieRequested` 0, `movieIsPlaying` 0, `movieIsCompletelyFinished` 1) and `CMovie::Play/Update/End` (0x210090/0x210408/0x210360) for the movie on the menu's big screen (`mov/sheldemo.pss`, looping). `Update` redoes `moviesSetScreenObject`: the big-screen object gets texId 999 (TEX0 CT32 at 0x3BA0, 256x128), which `Scene` replaces with the player's texture.
- **Format:** video 0xE0 (MPEG-2 via `libavcodec`, BT.601), audio in private stream 0xBD (`SShd`/`SSbd`, 16-bit PCM 48 kHz stereo in blocks of 512 bytes per channel, which FFmpeg does not recognize). [FORMATS.md](../FORMATS.md) ("Filmes .PSS" (.PSS movies)), `tools/pss.py`.
- **Runtime:** `PS2X_FMV=1` (`wotmFmvInstall`; takes precedence over `PS2X_SKIP_MOVIES`/`SKIP_CMOVIE`; in `wotm.exe` it turns on by itself if none of the three is defined, [BOUNDARY](BOUNDARY.md) step 9); `.PSS` from the disc folder or the ISO (`PS2X_CD_IMAGE`; `WOTM_DISC`/`WOTM_ISO` force it), `WOTM_FMV_MUTE=1`. Skip: Space/Enter/cross/start (`skip_` -> `continuar = 0`), from the raylib keyboard/gamepad or from the pad the game reads (`inputPadData`, a new press of X/Start: works for the `PS2X_PAD` script), without the 600-frame wait that `uiMain` imposes on `intro_m`; the "Sony presents" and "trademark" screens are the first ~10 s of `intro_m.pss`.
- **Pitfall fixed:** `Movie::close` must zero the L/R pair being assembled (`blk_`), otherwise the next movie comes out with hiss.
- **Missing:** the audio follows the wall clock, not the game's; the blocking `playMpegMovie` (0x20F440, no caller) was left out.

## Camera and snapshot
- **Camera:** `worldToScreenMat` embeds the axes (row 0 = 384·right + 2048·forward, row 1 = −180.48·up + 2048·forward, row 3 = forward; in the menu the horizontal focal length is 496). The vertical FOV comes from the matrix itself (63.6° in gameplay); do not mix it with the `_cs` read at another instant. **The eye comes from `worldCtx[view].eo`** (+0x20, = −`cs->trans`), which `viewUpdate` writes together with the matrix, and forward and up come from the matrix itself. The `_cs` only serves as a fallback in the menu. In the fight intro (the camera rising along the building), the game puts another camera into the same `_cs` (0x800d30) for an instant in the middle of the frame. The matrix still has the right one. The native read caught that instant, sometimes halfway (x and y from one camera, z from the other), and the screen cut for one frame to another corner of the map: 14 times in 50 s with the raw `_cs`, none with `eo`. The `[cam]` of `WOTM_CAMLOG` includes `cs=` (pointers of views 0 and 1), `wm3=` (the matrix's forward), `csp=`/`csu=` (position and up of the `_cs`).
- **Presentation rate (2026-10-18, `wotm_live.inc`, `initPresentRate`):** the window presents at the monitor's rate (`GetMonitorRefreshRate`; `WOTM_HZ=<n>` fixes it) with vsync (`WOTM_VSYNC=0` disables); before, it was the fixed `SetTargetFPS(60)` of `ps2_runtime.cpp`, without vsync, which beat against the monitor. The game logic stays at 60, so the scene is only **redrawn** when a new snapshot arrives (or when the `Shell::FadeScreen` fade changes, with the free camera paused, with the window resized, or at ~60/s if no frame has arrived for 40 ms: pause and loops without capture); in the other presentations the last image is just presented again. The cost stays that of 60, and texId 0 (previous frame) is still the previous drawing. Measured on a 180 Hz monitor (AI vs AI fight): ~176 presentations and ~60 redraws per second, game time 100% of real time; menu up to the fight the same (`docs/screenshots/2026-10-18/2026-10-18_apresentacao_180hz_luta.png`). `PS2X_STATS` shows `redesenhos=` (redraws) on the `[native]` line and, every 300 presentations, the average time of each redraw with 1 and 2 views (wall and CPU of the window thread; `[native] redesenho:` (redraw)). The runtime's per-presentation counters (`PS2X_SHOT_FRAMES`, `PS2X_COVERAGE` every 300, `PS2X_DUMP_RAM`) count presentations, which are now 3 per game frame on a 180 Hz monitor. Intermediate frames: interpolation between two snapshots (`WOTM_INTERP`, table below). The launcher detects the main monitor's resolution and rate (current mode, in real pixels) and, with no saved configuration, suggests the largest resolution that fits it.
- **Widescreen (Hor+, 2026-10-16):** the native frame is 720 tall (`WOTM_RES` changes it) and as wide as the aspect ratio (`wotm_live::viewAspect`): the vertical FOV is the game's and raylib widens the horizontal one by the render target's aspect ratio. The window opens at 1280x720 and the aspect ratio follows the window (from 4:3 to 32:9); `WOTM_ASPECT=L:A` fixes it (`4:3` = original screen). The GS screen (640x224) becomes the central 4:3 strip of the frame (`gsScreenRect`, `wotm_fx.hpp`): game text, lens flare (Z test and sprites) and the UV of the previous frame (texId 0) go there; the `hier` HUD is already in it because it is projected in front of the camera. Native collection does not cull by the game's frustum, so the sides appear whole; only particles go through `viewInFOV`, which in widescreen replaces the side planes (`planes[0][1..2]` of `viewSetFov`) with those of the wide screen (`Particles::inViewFov(..., wide)`). The game does not change (the AI and retail's `viewInFOV` stay at 4:3). Limits: the lens flares come from the game's list, projected and clipped at 4:3 (a source only on the sides does not shine); the replay (`--vu1cmp`) forces 4:3 (`g_force43`), because the GS reference is 4:3.
- **Split screen (2 players, 2026-10-19):** the game uses two views side by side, 320 x 224 of the GS each (`viewDef[1]`/`[2]`: centers 1888 and 2208, `fov` 352; the names `VIEWPORT_TOP/BOTTOM` in `view.cpp` are misleading). `TheGame::gameReestablishViews` creates them in modes 3, 6 and 7 (`m_gameMode`); the cinema scenes (`doCinema`/`endCinema`) toggle the split (`viewToggleSplitScreen`), so the fight intro comes out fullscreen; with the monsters close together (`gUseUnifiedView`) `viewGrappleConfig` puts view 0 in fullscreen (`viewDef[5]`) with both HUDs. `rtMain` runs each view's `hier(v, 0)` in the same frame, view 1 already after view 0's `gameUpdate`. In native: (1) **view per thread:** `wotm::ViewCtx`/`ViewScope` (`wotm_native.hpp`) say which view collection and drawing follow (camera, sky from `worldCtx[v]`, point lights, fog, alpha OT order, environment map with the view's center, the "ghost" buildings' sight lines, sphere culling with the view's half width and center; for particles, view test, strite, line and lens flare from `lensFlareIndex/Packet[v]`); `gsScreenRect` uses the view's aspect ratio (2:3 in the half). Without `ViewScope`, full view 0 applies, as before; (2) **capture:** `wotmCaptureScene(rdram, v)` at the exit of `hier(0, 0)` and of `hier(1, 0)` (fallback: entries of `TheGame::Update` and `Update2`), one collection `Scene` per view; view 1's snapshot goes in `Snapshot::view1`, with particles culled by its view and the same shadow copy; the published text is that of both views (`wotmFontDma`: view 0 comes out with view 1's last one); (3) **drawing:** each view in a texture of half the frame (what measures the framebuffer, such as the flares and the camera's aspect ratio, does not change), composited side by side; on top, the black strip of `Hud::buildSeparator` (6 GS px at the right edge of view 0, up to the center), the fades and the text. In split screen, a fade touching an edge of the game screen extends to the edge of the window (`Scene::splitEdges`). In widescreen each half grows sideways (Hor+). The free camera (F5) shows only view 0 full, and damage numbers (`WOTM_DAMAGEPOP`) do not appear in split screen. Checked with `WOTM_MATCH=3,1,1 WOTM_PLAYERS=2` with and without `WOTM_AIVSAI=1` (`WOTM_SHOTS`): split with HUD and "WINS" per view, cinema in fullscreen, alternation with the unified view, 60 frames/s; corpus unchanged. Pictures in `docs/screenshots/2026-10-19/`. **Lines and strites:** the tail uses the view's matrix from the previous `particleDraw`, which the game keeps in `D_0078F5A0[vista]` and copies into the system's packet (`fx + 0x2EC0`); there is only one packet, and view 1 wrote its own over view 0's (the sparks of Robo-47's shot became long streaks in the left view). Checked live by the owner (CANYON2 and METRO with Robo-47). Corpus: `split_linhas_robo47`, `split_linhas_robo47_2`, `split_barras_borda`, `split_barras_meio` and `split_barras_canto` (split lines / bars at the edge, middle, corner; the check only sees view 0 in fullscreen: they match 50-81% because the reference has both views, and the bars come from live hooks the replay does not run; they serve to notice change, not as a criterion). Pending: the lens flare debounce (`flarePrev_`) is a single one for both views; the game text in split screen ("WINS") still uses the 4:3 strip of the whole window.
- **Per-player controls (2026-10-19, `wotm_pad.inc` + `ps2_pad.cpp` from the patch):** before, the runtime ignored the `scePadRead` port and both ports received controller 0 plus the keyboard. - **2-player side selection (2026-10-19, `wotm_padsel.inc`; picture in `docs/screenshots/2026-10-19/2026-10-19_escolha_de_lados_2p.png`):** when entering the 2-player menu (screen 5) from the main menu, the big screen first shows the connected controllers and the keyboard, one per row, in the middle, between the PLAYER 1 and PLAYER 2 boxes. - **`native/wotm_fx.hpp`** (`Scene::fx`): cut before `particleDraw` (0x21B378). Gathers the active systems with `particleDraw`'s tests (including `viewInFOV`) and draws last (tests depth, does not write it, from farthest to nearest). ## Text and menu buttons
- **Text:** since 2026-10-18 it comes from the font hooks (`wotm::FontText` in `wotm_native.hpp`; hooks in `wotm_overrides.cpp`): `fontInitPacket` (TEX0 of the boot atlas), `fontSetTexId` (atlas from the `.RTX`), `fontSetColorGifTag` (color; with the packet empty it rewrites the header color, which applies at the start of the next frame), `fontBuildPrim` (one glyph, with the same computation as the original from `fonts[2]` and the current view's `viewDef`) and `fontDmaFontData` (closes the frame). Checked against the packet over 2,400 frames from the menu to the fight (26,267 glyphs, no difference). The replay (`--vu1cmp`) still reads the snapshot's `fontPacket` (`Scene::updateText`). The `ScreenPolys` HUD comes the same way, through the `polyBuildPrim` hook (`wotm::screenPolyFromCall`: `resolveFX` and the sprite redone from the arguments; 4,756 quads identical to the packet); the replay reads `s_polyBuffer` (`readScreenPolys`). Packet format: A+D tag (`TEX0_1` = PSMT8H 512x512 atlas), `[PRIM,RGBAQ]` + color, `[UV,XYZ3,UV,XYZ2]` with `NLOOP` sprites (12.4). 640x224 screen: `x - 1728`, `y - 1936` (split screen not handled yet). Color: the GS does texture·color/0x80 and saturates, so the shader doubles the RGB.
- **Button icons:** `CS` from the `McButtons` pool (ids `0x1F51..0x1F54`, `0x240E..0x2411`) placed by `AlignCsWithView` ~80 units in front of the camera; they ended up below the drive-in floor. They go to `Scene::overlay`, drawn last without depth. **Fade:** `screenSetButtonAlpha` copies `targetAlpha` to `+0x4C` of the child object; `drawList(..., fadeByNode=true)` multiplies the alpha by that float.
- **Fades (2026-10-16):** the game darkens the screen with an untextured GS SPRITE (ABE, `ALPHA_1` 0x44, color over the whole view, alpha 0x80 = covers) built on the spot: `rtFadeScreen` (fight entry, alpha 0x80 − 2·g_frame), `TheGame::updateFadeOut`/`updateFadeOutAndIn` (end of round, cinemas, camera change) put the packet in the `gsPkt` queue; `uiFadeScreen` (menu entry) builds it on the stack and sends it directly; `Shell::FadeScreen` (menu → level, end of loading) is its own loop that waits for vsyncs. Since 2026-10-18 native rebuilds the rectangle from the arguments, without reading a packet (hooks in `wotm_overrides.cpp`, computation in `wotm_live.inc` with `wotm::viewFadeRect`): `rtFadeScreen(vista, quanto)` and `uiFadeScreen(quanto)` (view, amount) give alpha 0x80 − amount over the whole view; `TheGame` is read on return from `updateFadeOut`/`updateFadeOutAndIn` (level at `+0x120450`, one view per player, only view 0 with a movie or a single view); the list goes in the snapshot (`Snapshot::screenRects`). `Shell::FadeScreen` does not go through the capture: the entry stores view, color, start, end and step, and each `sceGsSyncV` of the loop advances the alpha (`wotmShellFadeStep`/`wotmShellFadeStepDone`); the presentation uses that alpha until the next capture. With `b = false` it does not redraw the scene and repaints the fade over the same buffer every field, so the darkening accumulates (Π(1 − a/128) over that buffer's alphas) and native draws the equivalent alpha. `Scene::drawScreenRects` draws after the text; a rectangle as wide as the screen covers the whole window (widescreen), a smaller one stays in the 4:3 strip. Checked on screen (`docs/screenshots/2026-10-16/2026-10-16_fades_menu_e_entrada_da_fase.png`); the VU1 vs native check does not see the fades (replay without the hooks). **Level load (2026-10-18):** the "green sphere" of the loading screen (and the green, red or white light in the center of the screen at match entry, which changes with the level) was the `LOAD` card redrawn after `Shell::LoadLevelFiles` had already put the new level in RAM. `loadResources` swapped the textures for the level's, and the card came out with some arbitrary texture of the level (in CENTRAL, the power-up glow). On the PS2 the screen stays frozen on the card's last frame: the load bar is drawn directly into the frame, without `hier`, and the `FadeScreen(0, false, ...)` after `FinishLoadBar` only darkens that image. Now, from the entry of `LoadLevelFiles` to the entry of `rtMain` (hooks in `wotm_overrides.cpp`, `wotmLoadFreeze`), the capture publishes nothing and the presentation repeats the last drawn frame, with the `Shell::FadeScreen` fade on top. The load bar still does not appear (it does not go through native drawing). The card's fade-in (the `FadeScreen` with the `DisplayLoadBackground` redraw, which does `hier(0, 0)` and `sceGsSyncV` per step, without `timerWaitForMinUpdateRate`) did not reach native: the `sceGsSyncV` hook recognizes the loop's two return addresses and publishes the step's scene without turning off the fade (`wotmCaptureFadeStep`).
- **Menu black bars (2026-10-17):** in the menu the cinema bars are not the HUD's `Letterboxing` (that one is for the cinemas and intros of story mode) but `letterboxDmaData(alfa)`, which `userintMain` calls between `hier(0,0)` and `hier(0,1)`: two black 24-line SPRITEs at the top and bottom of the view, alpha `alfa·128`, without A+D (it uses the `ALPHA_1` 0x44 in effect). Rebuilt at entry from the alpha in `$f12` (`wotmLetterbox`) and drawn with the `underText` rectangles: after the scene, before the high-priority list and the text. They cover the width of the view, so in widescreen they span the window from side to side.
- Old menu pending items, not rechecked after the fixes: logo and "player 1" without color, dark and grainy cars (maybe reflection maps), wooden lattice with dotted alpha (texId 166; probably original).

## Projected shadows
- **Retail (`common/ps`):** up to 10 blockers in `psBlkLst` (0x51C600, 0x30 B: `cs` +0x10, second `cs` +0x18, radius +0x20, factor +0x24 (9), range² +0x28 (1200²), in-use u16 +0x2E; `psBlockerAdd`), drawn from the light's direction (`psLitDirWs`, 0x54CC90; view 4) into a small texture, filtered and reprojected onto nearby objects. Active if `psSetShadowOnOff` (0x6F8D7C), `cs->drawMe` and the view's bit in `cs+0xE`. Intensity `psShadowIntens` (0x6F8820) = 80.
- **Native:** `Scene::collectShadows`/`drawShadows`: only objects without `dontCastShadow` (bit 29 of the OBJECT bits at +0xC; `psBldBlkRObjs` skips them: on Kineticlops only the eye casts) enter the silhouette, rasterized on the CPU (128x128, orthographic, half side `raio * 1.1` (radius), two 3x3 box passes) and reprojected onto the objects whose sphere crosses the shadow cylinder. Differences: orthographic (retail: perspective with `psZoomT`), approximate filter, silhouette LOD. **Validated only with a synthetic scene.**
